# 幸福小Molly

个人日程 PWA，使用 React 19、TypeScript、Vite、IndexedDB 和 Supabase。支持执行今天、准备明天、按日期查看计划、三餐、补剂、健身、自定义事项、休息日家务、复制昨天、选项管理及业务备份。编辑使用底部面板，选项页从日程页右上角进入。

**账密改造源码与本机自动验收已完成（2026-10-13），本次尚未执行生产迁移、W 账号准备、远端环境更新或发布。** 现行方案见 [账密改造详细执行文档](docs/43-账密改造详细执行文档.md)，实测与部署交接见 [本地实施记录](docs/44-账密改造本地实施与部署交接.md) 和 [HANDOFF.md](HANDOFF.md)。历史 S1-S6 报告中的本地注册、双身份绑定和换设备重新注册流程已被本次方案取代。

## 启动

1. 安装依赖：`npm install`。
2. 开发环境配置 `VITE_SUPABASE_URL` 和 `VITE_SUPABASE_ANON_KEY`。
3. 启动：`npm run dev`，以 Vite 输出的浏览器地址为准，通常为 `http://127.0.0.1:8800`。
4. 登录可信管理入口已准备的账号 `W`。首次登录需要网络和有效的 Supabase Auth 配置；没有配置时会显示原因，不能本地注册绕过。

本机验收脚本使用隔离的假 Auth 与假云端，无需生产密码或管理员密钥。已有部署凭据继续使用受保护的本机配置，不重复向用户索取，不打印具体值。

## 账号、会话与数据归属

- 页面只使用「账号」和「密码」，仅接受 `W` / `w`；活动资料与同步状态只保存用户名 `W`，不暴露 Auth 内部标识。密码原样传给认证服务，不做 trim，不存入源码、前端环境变量或本地资料。
- Supabase Auth 是唯一认证来源。账号资料、业务根表、同步状态和待上传队列使用同一个 Auth UID；子表按父链检查归属。服务端使用受保护的 UID allowlist，客户端账号校验不能代替 RLS。
- 首次登录、退出后重新登录需要网络。启动会验证持久会话；新设备或未初始化的工作区先恢复该 UID 的云端数据，准备完成后才开放业务页。恢复失败不能当成云端为空，也不能先播种再覆盖云端。
- 已完成准备的工作区可在暂时断网时使用离线缓存，编辑仍存本地。离线缓存不验证密码，不代表新的登录成功，也不允许上传；联网重新核验身份后再补传。
- 普通退出关闭本机工作区，保留业务数据和未上传队列。同账号再次认证后打开原工作区；旧 localStorage JSON 不能重新创建已验证会话。

`DB_VERSION = 8`，共 18 张仓库：10 张业务数据、`users` 资料缓存、7 张设备/隔离/迁移状态仓库。v8 将旧账号和旧同步状态隔离，移除活动密码认证信息。旧业务数据保留以供盘点，不能通过“账号只剩 W”猜测归属或自动合并。明确旧 owner 与目标 UID 后才能执行受保护的迁移；目标已有数据或关联冲突时拒绝静默覆盖。

新业务备份为 **v3**，不含密码或 token，继续只读兼容 v1/v2。导入经过全量字段、父子关联和 ID 冲突校验，以当前已验证 UID 为归属，不从备份创建账号或会话。被清除且从未上传的编辑无法凭账号恢复，重要内容仍应保留独立备份。

## 服务层与上传

IndexedDB 仍是业务唯一写入落点，`DATA_BACKEND` 恒为 `'local'`。认证需要 Auth；日程读写仍通过本地业务服务完成。上传是增量上行通道，手动整体替换继续要求确认损失范围和「不可撤销」。新设备的首次恢复只针对尚未初始化的工作区，不构成通用自动双向合并。

```text
src/services/
  capabilities.ts  唯一的 Supabase 构建期环境变量读取点
  contracts.ts     页面接口与状态契约
  api/             界面唯一入口，认证/同步编排动态加载
  local/           资料缓存、IndexedDB、业务服务、备份及工作区迁移
  sync/            Auth 生命周期、工作区准备、上传与整体替换
  cloud/           errors / identity / rpc / supabase 四个传输模块
  session.ts       已准备的运行时身份与代次，不负责密码认证
```

本地写入口在事务内记录待上传项。推送固定 owner 与身份代次，读取主表最新行，先发 delete 再发 upsert，按依赖排序后切批次。身份变化后旧异步结果不得清新队列或写新工作区。全局调度器在 `main.tsx` 接线；状态卡片读取本地状态，明确的认证、首次恢复和上传才请求云端。

本地保存、认证成功、上传完成和恢复完成分别表述。队列为空只说明本机队列已排空，不能宣称「已同步」。

只有一个 Vite 构建。`npm run build` 生成 `dist/`；`npm run build:no-empty` 覆盖写构建产物，供 PWA 验收使用。Supabase SDK 保持动态加载。无 Auth 配置的构建可渲染配置错误页面，不能作为功能完整的本地登录版本发布。

`verify:sql` 串行启动临时 PostgreSQL，真正执行迁移并验证表、RLS、GRANT、四个 RPC、门禁默认拒绝、允许 UID 与旧 UID 的访问边界、备份 v3 往返、历史日期豁免和子表跨 owner 关联拒绝。需要 PostgreSQL 16+，可用 `MOLLY_PG_BIN` 指定；缺依赖或失败即报告失败，不能静默跳过。它不连接生产 Supabase，不能证明托管 Auth、schema cache 或真实部署状态。

浏览器脚本结束会关闭自己的临时服务和浏览器。`CHROME_PATH` 可指定浏览器，`APP_URL` 可指定现有开发服务；设置 `SHOT_DIR` 可保留截图。需要核对真机行为时仍要在手机上执行人工验收。

## 人工验收

1. 配好可信 Auth 与 W 门禁后用 W 登录；错误密码必须失败，不出现注册或二次绑定入口。首次准备失败时不能进入业务页。
2. 准备明天的三餐、补剂、健身、晨间和自定义事项，刷新确认本地恢复；执行今天的勾选独立于准备状态。
3. 确认历史日期只读；复制昨天保留内容快照，不复制准备/完成状态，也不改目标日期模式。
4. 核对选项增改、排序、启停与删除、补剂实例化、正常休息日家务和临时不上班规则。
5. 生成 v3 备份并检查无密码/token；导入后当前 UID 的业务数据整体替换。非法或关联冲突的备份必须一条不写；v1/v2 仅恢复业务，不恢复旧身份。
6. 断网前打开已准备工作区，断网编辑应保存本地且队列保留；恢复网络重新校验身份后补传。退出再用原账号登录，本地资料、业务与待上传项应保留。
7. 确认样本已上传并保留独立备份后，在全新浏览器或测试设备用同一个 W 登录，应恢复原 Auth UID 下的云端数据。不能把从未上传且被清除的本地编辑当成可恢复数据。
8. 使用受控测试旧 UID/JWT 直接检查服务端读写及四个 RPC 被拒；登录界面只接受 W 不能代替这项 RLS 验证。生产旧数据去向和 UID 迁移另行盘点，不通过清空站点或删除 Auth 用户处理。
9. 在真实 HTTPS 域名核对首页、SPA 深链接、SW/manifest 的 `no-cache`、assets 的 `immutable`，以及新旧应用壳更新流程。
10. iOS Safari 添加到主屏幕，Android 检查安装流程，核对独立窗口、存储状态、软键盘、抽屉保存/取消和安全区。安装不能替代业务备份。

# 幸福小Molly（本地业务开发）

此工程包含账号认证、Asia/Shanghai 日期引擎、日期模式、固定周一至周日周视图、工作日规划闭环（五项准备状态、三餐多选食物与备注、补剂模板实例化与逐项勾选、健身多选项目与备注、晨间事项、自定义事项）、休息日家务（拖地 / 洗衣）、复制昨天、选项管理（常用食物 / 固定补剂 / 健身项目的新增、改名、排序、启停、删除，按账号隔离）、本地数据导出 / 导入备份。导航为底部固定三入口（今日 / 本周 / 选项），编辑统一走底部面板并锁定背景滚动。业务数据可跑在两种后端上：**默认本地**（浏览器 IndexedDB，当前 `DB_VERSION = 4`，共 11 张对象仓库，不依赖网络），或 `npm run dev:cloud` / `npm run build:cloud` 切到 **Supabase**（适配器与本地逐条等价，页面代码不变——见下节）。

## 启动

1. 安装依赖：`npm install`
2. 启动：`npm run dev`
3. 在页面中注册本地测试账号。数据仅保存在当前浏览器的 IndexedDB 中。

浏览器地址通常为 `http://localhost:5173`。该地址由 Vite 运行输出为准。

## 数据后端：本地（默认）/ 云端

服务层现在分成两侧，**页面只 import `src/services/api/` 这一层门面**，不知道底下是谁：

```
src/services/
  contracts.ts   契约：函数名只写一遍，签名从 local 实现取；云端少一个函数就 typecheck 失败
  backend.ts     当前后端（由构建模式决定）
  api/           门面，页面只认这里
  local/         本地实现（IndexedDB），默认
  cloud/         云端实现（Supabase），与 local 逐条等价，parity.ts 做编译期断言
```

后端由**构建模式**决定，不需要改代码：

```bash
npm run dev          # 本地后端（默认）
npm run build        # 本地后端产物
npm run dev:cloud    # 云端后端（需要 .env.local 里的 VITE_SUPABASE_URL / VITE_SUPABASE_ANON_KEY）
npm run build:cloud  # 云端后端产物
```

两种后端的产物互不污染，可用产物检索核对：本地构建里搜不到 `supabase` / `GoTrueClient`，
云端构建里搜不到 `indexedDB` / `happy-little-molly-local`。

云端上线要在真实项目上执行 `database/migrations/` 里的四个 SQL（**按文件名顺序**：
`stage1_auth_sync` → `stage2_day_plans` → `stage3_workday_planning` → `stage4_local_parity`），
再补做跨设备同步、断网失败、RLS 双账号验收。上行迁移（把本地备份导入云端账号）与冲突处理
见 `docs/13-L6-cloud-migration-and-conflict-plan.md`；**该方案已定稿但尚未在真实项目执行**。

`npm run check:local-data` 同样直接导入源码，断言 IndexedDB 迁移表「只追加」（`DB_VERSION = 4` 与迁移表自洽、v1/v2/v3/v4 迁移不被改写、11 个仓库定义与迁移表一一对应）、三张选项表 + 三张每日内容表 + 家务表带 `user_id` / `day_plan_id` 索引，以及界面层没有直接引用 `localDb` / `indexedDB` / 云端 SDK、没有写死任何示例选项名称。示例选项清单自 L6 起提到 `src/services/optionExamples.ts`，本地与云端两侧播种共用同一份。

`npm run check:cloud-parity` 是纯静态检查，守住 L6「云端适配器与本地等价、页面不改业务接口」这条承诺的四个易失效点：① 契约里的每个函数名两侧实现都真的导出（文本复核一遍，防止用类型断言绕过）；② 页面没有绕过门面直连 `services/local`；③ `@backend` 只出现在门面目录（`vite.config.ts` 用的是相对替换，换地方引用就会指错）；④ 云端 SQL 覆盖全部 11 个本地仓库、每张表都开了 RLS、日期相关表与 L6 新增子表都挂了历史日期触发器、引用选项的外键是 `on delete set null`、复制昨天已换成覆盖新增表的 `copy_yesterday_stage4`。

`npm run verify:local` 会自动挑一个空闲端口拉起本项目的 Vite 开发服务器，并拉起本机 Chrome 或 Edge 的无头实例，实际走一遍
「v1 老库冷升级 → v2 升级 → v3 升级（含 backfillSnapshots）→ v4 升级（家务表）→ 登录页 → 注册 → 周视图 → 底部导航三入口 → 历史日只读 → 模式切换与恢复默认 → 切日期后保存状态归零 → 未来空日期引导 → 三餐多选食物与备注保存/恢复（面板滚动锁定）→ 补剂实例化与逐项勾选 → 自定义补剂增删 → 健身多选与备注 → 准备项进度（含补剂） → 自定义事项增改删 → 复制昨天不带准备/完成状态且保留快照 → 休息日家务（正常休息日自动带拖地洗衣 / 临时不上班不带 / 隐藏工作日准备项 / 可勾选） → 选项页增改排序启停删与补剂时段分组 → 备份往返（导出 → 改数据 → 导入还原停用状态）→ 备份卡片生成 / 非法文本被拒 / 空输入禁用检查 / 运行时契约拦坏记录 → 刷新恢复 → 账号间选项隔离 → 桌面/手机视口无溢出 → 退出登录 → 清空站点数据后重新注册并导入备份完整搬家」共 94 项检查，
并检查控制台无 error / warning。结束时自动关闭浏览器与临时服务器，不残留进程、不占用固定端口。
其中冷升级用例会用浏览器调试协议把入口模块的响应换成空模块，让页面停在「同源但没跑应用」的状态，先造出一个真正的 v1 老库，再放开加载、由应用自己把它升到当前版本（v4），用来验证迁移只追加且老数据不丢（含 v2→v3 的 `backfillSnapshots` 自由文本转快照）。
若浏览器不在默认位置，用 `CHROME_PATH` 指定可执行文件；若想指向一个已在运行的服务，用 `APP_URL` 覆盖（此时脚本不再自建服务器）。
设置 `SHOT_DIR` 可把关键界面截图落盘，用于人工核对观感，例如 `SHOT_DIR=D:/tmp/shots npm run verify:local`；不设置则完全不写文件。

`npm run verify:pwa` 跑的是**生产构建产物**（先 `npm run build`，再用一个零依赖的静态服务器托管 `dist/`，端口同样自动申请），因此它和 `verify:local` 互补而不是重复：`verify:local` 走 dev server，而 service worker 刻意只在生产构建注册（dev 注册会让 dev server 上的两个既有用例失效）。它覆盖 42 项：dev 模式确实没有 SW 注册、manifest 字段齐全、图标全部 200、SW 处于 activated、Cache Storage 里有带构建戳的应用壳且不含任何跨域条目、CDP 模拟断网与**真的关掉服务器**两种断网下刷新仍能渲染应用、断网时仍能注册并读回已写入的本地数据、重新构建后新版本停在 waiting（不静默替换当前页面）且用户点「刷新」后旧缓存被清理、存储状态卡片如实显示用量 / 是否持久化 / 是否独立窗口、桌面与手机视口无横向溢出、控制台无 error / warning。同样支持 `SHOT_DIR`。

`npm run icons` 用本机 Chrome 无头模式把 `public/favicon.svg` 渲染成 192 / 512 / maskable 512 / apple-touch-icon 180 四张 PNG（不引入任何图像处理依赖），产物提交在 `public/` 下，脚本可重复执行。

## 验收步骤

1. 注册或登录后在"准备明天"完成五项准备（含补剂）、三餐（多选食物 + 备注）、晨间、健身（多选项目 + 备注）和自定义事项；刷新确认从本地数据库恢复。
2. 在"执行今天"确认完成勾选独立于准备状态；补剂和健身可逐项勾选执行；本周点击日期可回到完整单日页。
3. 使用"复制昨天"，确认计划内容（含食物/补剂/健身快照）被复制、五项准备和全部完成状态未复制，且目标日期模式与 `mode_override` 未改变。
4. 使用两个本地账号验证各自的三餐、自定义事项、补剂和选项（食物 / 补剂 / 健身）相互不可见；尝试新增、修改、删除历史从属记录必须被服务层拒绝。
5. 切到明天或更远的日期（尚未规划时）应看到「这一天还没有计划」引导块；勾选任意准备项或保存任一面板后，该引导自行消失。昨天及更早的日期只显示「历史计划仅供查看」，没有编辑入口。
6. 进入「选项」：新账号应已带出示例食物 / 补剂 / 健身项目；补剂按早 / 中 / 晚分组。尝试新增重名项应被拒绝且面板保留输入；停用与删除都需要二次确认，停用项仍留在清单里并把「启用 N 项」计数减一；刷新后清单、顺序与停用状态不变。
7. 打开补剂面板：应自动从模板生成当日实例（早/中/晚），模板来源的行不可删除；可添加自定义补剂行并可移除；保存后刷新确认实例与完成状态正确恢复。
8. 切到周六或周日（正常休息日）：应自动出现「拖地」「洗衣」两项且仅需勾选完成；没有衣服/三餐/晨间准备项；补剂、健身和自定义事项仍可用。工作日手动切到休息日（临时不上班）：不出现拖地/洗衣，显示「临时不上班」说明；恢复默认后家务重新出现。
9. 进入「选项」底部的「本地数据备份」：点「生成备份」应得到带格式标记与来源账号的 JSON 文本；改几条数据后再粘贴原备份、点「检查这份备份」会列出备份内容与来源账号并需二次确认，确认后当前账号数据被整体替换、改动的数据回退；刷新后确认还原结果仍在。
10. 在同一个卡片里粘贴一段非法文本（比如随便打几个字），点「检查这份备份」不应弹确认框，而是给出可读错误且现有数据分毫不动；输入为空时「检查这份备份」按钮应处于禁用状态。
11. 备份也是唯一的「换设备」路径：在浏览器里清空本站点数据（等同换台设备），重新注册一个新账号，应拿到全新示例选项而不是旧账号残留；把之前导出的备份粘进卡片导入，选项清单与日计划内容（含准备项、三餐快照）应完整回到这个新账号下。
12. 进入「选项」的「存储与安装」：应看到本地存储用量、持久化存储是否已获得、运行方式是否独立窗口三项真实状态。桌面浏览器上是「浏览器标签页」，从主屏幕图标打开时是「独立窗口（已安装到主屏幕）」并显示「已经安装」。
13. 移动端（**必须真机**，桌面浏览器验不了）：用 `npm run build` 的产物部署到 HTTPS 地址后，在 iOS Safari 里点分享 → 添加到主屏幕，再从主屏幕图标打开——应没有浏览器地址栏、`display-mode: standalone` 为真，且「存储与安装」显示「独立窗口（已安装到主屏幕）」。底部导航不应被 Home 指示条盖住（安全区已在 `verify:pwa` 里用 CDP 模拟验收，真机只需确认观感）。这一条的目的是让本地数据进入独立存储分区，避开 iOS「7 天无交互即清空可写存储」的规则；**安装不能替代备份**，重要数据仍要用上面的导出留一份。
14. Android Chrome 上若浏览器给出了安装入口，「存储与安装」里会出现「安装到主屏幕」按钮，点击应触发系统安装流程。
