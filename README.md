# 幸福小Molly（本地业务开发）

此工程包含**账号 + 密码**认证（v5 起；此前是邮箱 + 密码，老账号由迁移原样承接，见下节）、Asia/Shanghai 日期引擎、日期模式、按日期查看计划、工作日规划闭环（五项准备状态、三餐多选食物与备注、补剂模板实例化与逐项勾选、健身多选项目与备注、晨间事项、自定义事项）、休息日家务（拖地 / 洗衣）、复制昨天、选项管理（常用食物 / 固定补剂 / 健身项目的新增、改名、排序、启停、删除，按账号隔离）、本地数据导出 / 导入备份。底部固定两个日程入口（执行今天 / 准备明天），选项从日程页右上角进入，并以独立页面显示，不带日程底栏；编辑统一走底部面板并锁定背景滚动。业务数据落在浏览器 IndexedDB（当前 `DB_VERSION = 7`，共 13 张对象仓库，**不依赖网络**）——S1 起本地是**唯一**的写入落点，云端不再是可切换的另一种后端，而是可选的上行通道（见下节）；S2 起每次本地写入都会在同一事务里进一张待上传队列，但**还不推送**。

## 启动

1. 安装依赖：`npm install`
2. 启动：`npm run dev`
3. 在页面中注册本地账号（3–20 位字母 / 数字 / 下划线，不区分大小写；密码至少 6 位）。数据仅保存在当前浏览器的 IndexedDB 中。

浏览器地址通常为 `http://127.0.0.1:8800`。该地址由 Vite 运行输出为准。

### 本地 PostgreSQL 仿真数据库

如果需要仿真线上 Supabase 的持久化结构，可以启动项目自带的本地 PostgreSQL：

```bash
npm run db:local:init    # 首次创建并执行六份迁移
npm run db:local:status
npm run db:local:start
npm run db:local:stop
npm run db:local:reset   # 备份旧数据后按当前迁移重建
```

默认连接地址为 `127.0.0.1:55432`，数据库名和用户名都是 `molly`。
也可以用 `npm run db:local:psql -- -c "select now();"` 查询。
详细说明见 [docs/本地数据库说明.md](docs/本地数据库说明.md)。这个数据库只用于本地仿真，
不会改变浏览器 IndexedDB 作为业务唯一写入落点的设计。

## 账号与密码（v5）

登录凭据是**账号 + 密码**，不是邮箱。账号规则集中在 `src/shared/authRules.ts`（本地与云端两侧、以及界面提示共用同一份，`check:local-data` 会断言这一点）：

- 新注册：3–20 位，只能用字母、数字、下划线；大小写不敏感（入库前归一成小写）。
- 登录：**不校验格式**。v5 之前注册的账号是从邮箱原样迁过来的，形如 `molly@example.com`，
  这批用户继续用原字符串登录即可——若登录也套新规则，他们会被自己的账号挡在门外。

`users` 对象仓库的字段与唯一索引都从 `email` 换成了 `username`，由 `DB_VERSION` 4→5 的迁移
（`localDb.ts` 的 `renameUsersToUsername`）同时改数据与索引；老记录**原样**改名，不做「取 @ 前面那段」的加工。

备份文件格式同步升到 **v2**（`source_user.email` → `username`）。**v1 的旧备份仍然可以导入**：
`parseBackup` 在读入时把 `email` 归一成 `username`，之后走完全相同的校验与写入路径，
不存在「为老文件放宽校验」的第二条分支；导入时会有一条「备份是旧版格式」的提醒。

云端侧 Supabase Auth 只认邮箱或手机号，因此账号被映射成合成邮箱 `<账号>@molly.local`，
真实账号名存在 `user_metadata.username`。这个域名定下后不能改，细节见 `services/cloud/authService.ts` 顶部注释。

## 数据后端：本地为落点，云端是可选上行通道

页面只 import `src/services/api/` 这一层门面。**S1 起门面直接指向本地实现**，不再按构建模式切换——
本地 IndexedDB 是唯一的写入落点，云端退化为可选的上行通道（自动上传 + 两个手动整体替换），
不参与页面的读写路径。

```
src/services/
  capabilities.ts  能力声明：数据落点恒为本地；云端同步是否已配置（构建期 env）
  contracts.ts     契约：函数名只写一遍，签名从 local 实现取
  api/             门面，页面只认这里（直接指向 local）
  local/           本地实现（IndexedDB），唯一写入落点
  cloud/           被冻结的种子：S4 会把它改造成同步传输层，当前只被同目录的 parity.ts 引用
```

只有一个构建，不需要选后端：

```bash
npm run dev      # 开发
npm run build    # 生产构建（→ dist/，会先清空 dist）
```

> `npm run build:no-empty` 是给 `verify:pwa` 用的变体（`vite build --emptyOutDir=false`，**不清空 `dist/`**）。
> 原因：验收脚本要构建两次，而 Vite 默认的清空动作在受沙箱保护的机器上会被批量删除保护拦下，
> 导致脚本在浏览器阶段全绿之后倒在最后一步。人工 / CI 仍用 `npm run build` 做干净构建。

`dev:cloud` / `build:cloud` 与 `dist-cloud/` 已随 S1 删除：两个后端不再互斥，
「按构建模式二选一」这件事本身就没有了。

本地优先现在由一条**更强的判据**守着：**未配置云端账号时，整轮交互零跨域请求**。
`verify:local` 用 CDP 监听网络并断言非同源请求数为 0；`check:cloud-parity` 静态断言
`@backend` 别名已移除、引用 `services/cloud` 的只允许是 `services/sync/`，
且同步门面（`api/syncService.ts`）必须用动态 `import()`——
因此 `supabase` 只出现在按需加载的 chunk 里，主 chunk 仍然搜不到 `supabase` / `GoTrueClient`。
（旧判据「本地产物 0 命中 supabase」只证明代码没打进产物，新判据证明**运行时也不会偷偷联网**。）

云端上线要在真实项目上执行 `database/migrations/` 里的四个 SQL（**按文件名顺序**：
`stage1_auth_sync` → `stage2_day_plans` → `stage3_workday_planning` → `stage4_local_parity`），
再补做跨设备同步、断网失败、RLS 双账号验收。上行迁移（把本地备份导入云端账号）与冲突处理
见 `docs/13-L6-cloud-migration-and-conflict-plan.md`。

从「本地单机」升级到「本地 + 云端同步」的完整方案与任务线见
`docs/18-sync-architecture-plan.md` 与 `docs/19-sync-execution-plan.md`。
**方案已定稿，S1–S5 已落地**（架构切换与能力声明 → 本地变更追踪 → 云端账号绑定与连接 →
自动上传 → 双向整体替换），**只剩 S6（部署与真机验收）**。S6 没有代码可写，
缺的是真实 Supabase 凭据与真机环境——`docs/25-S5-completion-report.md` §6 把剩下的清单列全了。
S2 的完成报告见 `docs/21-S2-completion-report.md`：本地新增 `sync_outbox`（待上传队列）与
`sync_state`（同步状态）两张**设备状态**表，13 张仓库按「用户数据 / 元数据 / 设备状态」三分类拆开，
三个写入口（`put` / `remove` / `runTransaction`）默认在同一事务里记一条队列记录，
压缩与层级排序规则抽成纯函数由 `npm run check:sync` 守。
S3 的完成报告见 `docs/22-S3-completion-report.md`：「账号与同步」子屏新增云端同步卡片，
未配置 Supabase 时直说不可用；配置了则可以连接 / 新建云端账号、看清两边各有多少条、
按三种情形给确认文案，连接后显示「待上传 N 条」。**S3 只连账号、不动数据**，
上传与恢复是 S4/S5 的事——所以此时应用**仍然不发任何网络请求**。

`updated_at`（那是云端自己的列，本地契约里没有也不该有）。

```bash
npm run typecheck           # 类型检查
npm run lint                # 静态检查
npm run build               # 生产构建
npm run check:dates         # 日期引擎规则回归（48 项，无需浏览器）
npm run check:local-data    # 本地数据结构回归（62 项，无需浏览器）
npm run check:backup        # 备份格式回归（62 项，无需浏览器）
npm run check:cloud-parity  # 数据层一致性回归（78 项，无需浏览器）
npm run check:sync          # 同步队列、归属规则、映射与文案回归（113 项，纯函数，无需浏览器）
npm run verify:local        # 真实浏览器闭环验收（125 项，自带临时开发服务器，无需先跑 dev）
npm run verify:pwa          # PWA 层验收（49 项，跑生产构建产物 + 自建静态服务器 + 部署配置）
npm run verify:sync         # 同步闭环验收（74 项，假云端 + CDP 拦截，验自动上传、失败补推、换账号不串推与双向整体替换）
npm run verify:sql          # 云端 SQL 真库验收（39 项，起临时 PostgreSQL 跑真实迁移与三个 RPC，需本机装 PostgreSQL 16+）
npm run icons               # 由 public/favicon.svg 重新生成 public/ 下的 PNG 图标
```

`npm run check:dates` 直接导入 `src/shared/date/dateUtils.ts`（Node 22.18+ / 24 原生支持剥离类型），覆盖月末、年末、闰年、跨年周的日历运算，默认工作日 / 休息日判定，以及日期关系与非法日期拒绝。不需要浏览器、不需要构建产物。

`npm run check:local-data` 同样直接导入源码，断言 IndexedDB 迁移表「只追加」（`DB_VERSION = 7` 与迁移表自洽、v1–v7 迁移不被改写、13 个仓库定义与迁移表一一对应、`users` 的唯一索引是 `username`、本地与云端认证共用同一份账号规则）、仓库三分类（用户数据 10 / 元数据 1 / 设备状态 2）互不交叉且合起来覆盖全部 13 张表、每张表都有字段契约、两张设备状态表的索引与定义一致、写入钩子确实挂在 `put` / `remove` / `runTransaction` / `readModifyWrite` 四个入口上（且队列记录的字段校验发生在**任何写入请求之前**）、`clear` 命中用户数据仓库时必须显式 `track: false`（否则会静默漏记一批删除），以及三张选项表 + 三张每日内容表 + 家务表带 `user_id` / `day_plan_id` 索引、界面层没有直接引用 `localDb` / `indexedDB` / 云端 SDK、没有绕过契约与入队钩子的直接写库（`put`/`add`/`delete`/`clear` 四类一起扫）、没有写死任何示例选项名称。示例选项清单自 L6 起提到 `src/services/optionExamples.ts`，本地与云端两侧播种共用同一份。

两处**业务缺陷的回归**也在这里（`docs/24`）：

- **v7 搬迁规则**（`rekeySyncStateRows`，纯函数逐条钉死）：把 `sync_state` 的老行重新归属到登录中的本地账号、删掉旧主键那一行、已是新形状的行不动（幂等）、升级时没人登录就删掉。这条规则错了的症状是「换个账号登录就看到别人的云端绑定」，只有真机上换账号才会暴露，而那时数据已经推到别人的云端账号里了——所以规则本身必须能在 Node 里回归。
- **读-改-写的原子性**：`readModifyWrite` 必须先读、再算、再校验、最后才发写入请求（顺序写歪就会留下脏数据或「数据写了队列没记」）；`upsertDayPlan` 必须走它并按 `user_date` 唯一索引读，`setMealCompleted` 同理（`daily_meals` 的 `plan_type` 也是唯一索引）。

`npm run check:sync` 是 S2 新增的纯函数回归（不碰 IndexedDB、不碰网络）：可入队的仓库正好是 10 张用户数据表、`users` 与两张设备状态表都不入队；压缩规则（同一 `(store, record_id)` 只留最后一条、`attempts > 0` 的条目不参与压缩、批内「先删后写」收敛成 `upsert`）；依赖层级排序（写入按父表→子表、删除按子表→父表、同层按 `seq`）；序号在时间前进时严格递增；设备仓库进不了备份（手改备份塞进 `sync_outbox` 会被整份拒绝）；两个新仓库的字段契约（队列里放不进 `users`、放不进 `payload` 这类数据副本）。S3 起追加**绑定情形判定**（`sync/bindingRules.ts` 的 `judgeBindingCase`：云端空 → `cloud-empty`、两边都有 → `both-sides`、本地空 → `local-empty`，两边都空归到 `cloud-empty`）——这条规则判错的后果不是报错，而是**让用户选错覆盖方向**，所以边界必须钉死。**它证明的是「规则正确」，证明不了「规则真的被调用」**——后者由 `verify:local` 在真实浏览器里断言。S4 起再追加四组：推送批次上限（100，理由是失败时的重试粒度而不是请求体大小）与队列变更事件名；**相对时间边界**（`shared/date/relativeTime.ts`：不足一分钟说「刚刚」、满 7 天不再用相对说法、未来时间戳不显示负数）；**同步文案口径**（S3 那句「还没有开始上传」必须已删掉、队列排空时的说明不能出现「已同步」、有待上传时承诺的是「继续自动上传」而不是「正在上传」）；以及**本地行 → 云端行的映射**（`sync/mapper.ts`：`user_id` 重写成云端账号 id、剔除云端遗留列 `exercise_content` / `plan_content`、子表不凭空加 `user_id`、映射不改动入参）。映射错了的后果很隐蔽——云端收到形状不对的行、PostgREST 报错、推送失败、队列堆积，而本地一切正常，所以这四条必须在 Node 里钉死。**队列条目的归属账号**（`outboxRules.entriesOfOwner`）也在这一组：只推当前本地账号的条目、没有会话时一条都不推、归属为 `null` 的老条目永不被推送。这条规则错了的后果是**跨账号串数据**，而界面上完全没有痕迹。同一组里还有 `sync_state` 的按账号分行（没有会话时读不到状态、空白状态的主键就是账号 id）——它比任何运行期判断都可靠：读不到别人的绑定，在结构上就不成立。S5 起再追加两组：**整体替换的前置规则**（`sync/replaceRules.ts`——映射到云端 `uuid` 列的那些字段必须真的是 UUID：`createId()` 在浏览器不支持 `crypto.randomUUID` 时会退回「时间戳-随机数」，那种 id 上传会死在数据库深处，报一句用户无法据此行动的 `invalid input syntax for type uuid`，所以提前拦下并说清是哪些字段；空的一侧也要拦住——用 0 条替换掉另一边等于一次「上传」把数据全删了，而且拒绝文案要指出正确动作是另一个按钮）与**云端快照必须能过 `parseBackup`**（`replaceLocal` 拿到快照后要整份校验才允许写本地；快照少了合成的 `users` 行、或多出云端遗留列，都会让「从云端恢复到本地」以「备份文件不合法」告终——而这一步在浏览器里只有真连上云端才走得到，所以必须在 Node 里先钉死）。

`npm run check:cloud-parity` 是纯静态检查。它守的既不是「两种后端可互相替换」（后端已经不互斥了），
也不是「云端有没有等价实现」（S4-T7 起那批适配器已整批删除），而是
**页面接口清单、同步传输层与云端 SQL 三者的对应关系**，共十组：
① 页面接口清单（`contracts.ts`）里的每个函数名在本地实现与四个门面里都真的导出（文本复核一遍，
防止用类型断言绕过）；② **云端目录只剩同步传输层四个模块**（`errors` / `identity` / `rpc` / `supabase`），
L6 遗留的页面后端适配器不许悄悄长回来；③ 页面没有绕过门面直连 `services/local`；
④ 四个门面整份转发 `../local/*`、`@backend` 别名已彻底移除、`vite.config.ts` 不再配 `resolve.alias`；
⑤ Supabase 环境变量只有 `capabilities.ts` 一处来源、旧的 `backend.ts` 已删除；
⑥ 引用 `services/cloud` 的只允许是 `services/sync/`（这条保证本地产物仍然不含 supabase）；
⑦ 云端 SQL 覆盖全部 11 张需要上云的表（10 张用户数据 + `profiles`）、每张表都开了 RLS **且有策略**、
每张表都有服务端 `updated_at` 与 `set_updated_at` 触发器、日期相关表与 L6 新增子表都挂了历史日期触发器、
引用选项的外键是 `on delete set null`、复制昨天在 SQL 里有覆盖新增表的 `copy_yesterday_stage4`
**且已无 TS 调用方**（整条链路在本地完成）；
⑧ 示例选项清单只有一份，播种只读它；
⑨ **列级对齐**（S4-T6）：本地字段契约里的每个字段在云端都有同名列、云端多出的列都能被省略（有默认值或可空）、
带 `user_id` 的云端表与映射层的 `USER_SCOPED_STORES` 完全一致、每张用户数据仓库都有推送映射。
第 ⑨ 组的理由：**表名对得上不代表推得动**——「本地有字段、云端无此列」的报错症状是
「本地一切正常、云端一条没有、队列越堆越长」，最难倒查；这组断言做过反证（临时移走 `stage5` 后
立刻以三张子表的名字失败），不是空断言。它读的是 `create table` **加** `alter table … add column` 两处，
只读前者会得出「云端缺一堆列」的假失败。

⑩ **双向整体替换的 SQL**（S5）：三个 RPC（`cloud_sync_summary` / `export_cloud_snapshot` /
`import_local_backup`）都存在、都显式声明 `security invoker`（**不提权**）、三处历史日期豁免都
**写在日期比较之前**、且豁免用事务级 `set local` 打开而不是永久开关。
这组的理由：这类开关写错方向**不会报错，只会静默放行**——写成 `security definer` 就把越权从
「不可能」变成「取决于函数体写得对不对」；豁免顺序反了等于没有豁免（函数会先在日期比较处抛错）；
豁免泄漏到事务外就变成「导入过一次之后，这个连接就能随便改历史」。
这一组是**静态**的，真正证明「它跑得起来、且豁免不泄漏」的是 `npm run verify:sql`（起临时真库跑一遍）。

第 ⑦ 组的仓库口径是「数据库全部仓库去掉设备状态」——
`sync_outbox` / `sync_state` 是本机状态，云端没有、也不该有对应表。

`npm run verify:local` 会自动挑一个空闲端口拉起本项目的 Vite 开发服务器，并拉起本机 Chrome 或 Edge 的无头实例，实际走一遍
「v1 老库冷升级 → v2 升级 → v3 升级（含 backfillSnapshots）→ v4 升级（家务表）→ v5 升级（登录名字段与唯一索引 email → username）→ v6 升级（两张设备状态表）→ v7 升级（同步状态改按本地账号分行）→ 登录页 → 注册 → 双入口日程导航（执行今天 / 准备明天） → 历史日只读 → 模式切换与恢复默认（工作日切休息日播放庆祝动效）→ 切日期后保存状态归零 → 未来空日期引导 → 三餐多选食物与备注保存/恢复（面板滚动锁定）→ 补剂实例化与逐项勾选 → 自定义补剂增删 → 健身多选与备注 → 准备项进度（含补剂）→ 执行项本地失败/重试、下一步变化、连续完成与撤销反馈 → 自定义事项增改删 → 复制昨天不带准备/完成状态且保留快照 → 休息日家务（正常休息日自动带拖地洗衣 / 临时不上班不带 / 隐藏工作日准备项 / 可勾选） → 选项页增改排序启停删与补剂时段分组 → 待上传队列（注册播种与删除都进队列，且只含用户数据仓库）→ 备份往返（导出 → 改数据 → 导入还原停用状态）→ 备份卡片生成 / 非法文本被拒 / 空输入禁用检查 / 运行时契约拦坏记录 → 刷新恢复 → 账号间选项隔离 → 账号与同步子屏（未配置云端时同步卡说明不可用、不出现「已同步」说法） → 桌面/手机视口无溢出 → 并发建同一天的日计划（10 个并发调用只落一行）→ 退出登录 → 清空站点数据后重新注册并导入备份完整搬家 → 整轮交互零跨域请求 → v6 老库真实升级到 v7（状态行重新归属到登录中的账号、旧主键被删掉）→ 控制台干净」共 125 项检查，
并检查控制台无 error / warning。结束时自动关闭浏览器与临时服务器，不残留进程、不占用固定端口。
其中冷升级用例会用浏览器调试协议把入口模块的响应换成空模块，让页面停在「同源但没跑应用」的状态，先造出一个真正的 v1 老库，再放开加载、由应用自己把它升到当前版本（v7），用来验证迁移只追加且老数据不丢（含 v2→v3 的 `backfillSnapshots` 自由文本转快照）。
「待上传队列」那两条是 S2 的运行时证据：`check:sync` 只能证明队列规则正确，证明不了规则真的被调用；
这里在真浏览器里读 `sync_outbox`，断言注册与播种产生的写入都在队列里、删除食物后出现一条 `food_options` 的 `delete`、且队列里一条 `users` / 设备状态记录都没有。
「整轮交互零跨域请求」是 S1 引入的新判据：用 CDP 的 `Network` 域统计非同源请求并断言为 0，
证明未配置云端时应用**运行时也不会偷偷联网**（不只是「代码没打进产物」）。
S3 起这条判据由同步卡片继续守着：卡片挂载时会读一次同步状态，而那条路径
（`sync/status.ts`）**纯本地、一个请求都不发**——「云端现有多少条」只在用户主动点了连接时才去问。
若浏览器不在默认位置，用 `CHROME_PATH` 指定可执行文件；若想指向一个已在运行的服务，用 `APP_URL` 覆盖（此时脚本不再自建服务器）。
设置 `SHOT_DIR` 可把关键界面截图落盘，用于人工核对观感，例如 `SHOT_DIR=D:/tmp/shots npm run verify:local`；不设置则完全不写文件。

`npm run verify:pwa` 跑的是**生产构建产物**（先 `npm run build`，再用一个零依赖的静态服务器托管 `dist/`，端口同样自动申请），因此它和 `verify:local` 互补而不是重复：`verify:local` 走 dev server，而 service worker 刻意只在生产构建注册（dev 注册会让 dev server 上的两个既有用例失效）。它覆盖 49 项（其中 6 条是部署配置断言：见下）：dev 模式确实没有 SW 注册、manifest 字段齐全、图标全部 200、SW 处于 activated、Cache Storage 里有带构建戳的应用壳且不含任何跨域条目、CDP 模拟断网与**真的关掉服务器**两种断网下刷新仍能渲染应用、断网时仍能注册并读回已写入的本地数据、重新构建后新版本停在 waiting（不静默替换当前页面）且用户点「刷新」后旧缓存被清理、存储状态卡片如实显示用量 / 是否持久化 / 是否独立窗口、目标日已确认为工作日、软键盘弹出时底部抽屉与居中卡片都让开键盘、桌面与手机视口无横向溢出、控制台无 error / warning。同样支持 `SHOT_DIR`。

部署配置六条（S6-T1 / T2，2026-09-20 落地，全部做了反证）：`vercel.json` 有一条通配 rewrite 指向 `/index.html`（SPA 深链接回退）；`vercel.json` 与 `public/_headers` 的缓存口径一致且 `_headers` 确实进了 `dist/`（service worker 与 manifest 一律 `no-cache`、`/assets/*` 一年 `immutable`）；产物里**没有**顶层 `404.html`（否则会静默关掉 Cloudflare Pages 的内置 SPA 回退）；产物里**没有** `_redirects`（刻意不写——Cloudflare 文档说 `_redirects` 规则「不管有没有静态资源匹配都会执行」，一条 catch-all 会把 `/sw.js` 与 `/assets/*` 一起改写成 HTML 导致整站白屏）。

`npm run verify:sync` 验的是 S4 的自动上传与 S5 的双向整体替换（74 项）。做法是**起一个假云端**：先向系统要一个空闲端口，用它既跑 Vite 开发服务器、又当作 `VITE_SUPABASE_URL`，于是 supabase 客户端拼出来的 `/auth/v1/*` 与 `/rest/v1/*` 跟页面同源（整条链路没有跨域，不需要伪造 CORS 头，也不需要给浏览器加会改变被测行为的 `--disable-web-security`），再用 CDP 的 `Fetch` 域按路径前缀拦下来，由脚本内存里的假云端应答。它覆盖：未绑定云端账号时不发任何云端请求（与 `verify:local` 的「未配置云端」是不同口径，后者验的是 origin）；绑定流程走界面（探测发的是 `HEAD` 计数而不是把数据搬下来、确认框文案、确认后清空绑定前积压的队列）；写入后队列在防抖窗口内被自动推空、云端收到正确行、`user_id` 被改写成云端账号 id；1.5 秒内连续两次改名在队列里收敛成一条且推的是最后一次的值；删除被推送为 `DELETE`；**断网**期间队列原地保留且不更新「最后上传」；恢复后自动补推；**云端返回 500** 时如实记下原因、队列不清空、界面上出现「上传失败：<原因>」；恢复后按退避自动重试并清掉失败原因；重复推送不产生第二行；设备状态表与本地账号表从未被推送；刷新后绑定关系仍在；**换本地账号不串推**（退出登录不清绑定，换到另一个账号后它看到的是「未连接」而不是上一任的绑定、写入只进队列不发请求、换回原账号后绑定仍在且另一个账号的待上传条目留在队列里没被推走）。控制台断言拆成两段（注入 500 之前必须完全干净、之后只允许出现那一条刻意制造的噪声），避免用「测试自己造的噪声」掩护真实错误。S5 起再追加**双向整体替换**（`replaceCloud` / `replaceLocal`，都只在用户点按钮并二次确认后执行）：确认框里的条数与假云端真实条数一致；确认后云端被整份替换、界面如实报出结果；确认后本地被整份替换、**本地独有的那条被删掉**（证明是替换不是合并）；**任一步失败都如实报错、绝不出现「已替换」**，且失败时两边数据一行没动。

`npm run verify:sql` 是**唯一一条真的连数据库**的验收（39 项，需要本机装 PostgreSQL 16+，可用 `MOLLY_PG_BIN` 指定 bin 目录；找不到就**直接失败，不静默跳过**——一个不跑的验收脚本等于没有，而「跳过」在 CI 上看起来和「通过」一模一样）。它向系统要一个空闲端口，用 `initdb` 起一个临时集群，打上 `auth` 垫片后按文件名顺序把 `database/migrations/` 里的六个迁移**真的执行一遍**，再断言结构与行为：10 张业务表都建得出来且都开了 RLS、都有策略；三处历史日期触发器都挂上了；三个 RPC 存在且都是 `security invoker`（**不提权**——一旦某个函数被写成 `security definer`，越权就从「不可能」变成「取决于函数体写得对不对」）；导入一份「每张表各一条、日期全在过去」的备份成功（这同时证明 `molly.allow_history` 豁免真的生效）；摘要口径与本地一致；**快照每张表的字段集合与本地 `recordSchemas` 逐张严格一致**（stage6 里那份字段清单是逐字手写的，多一列或少一列本地 `parseBackup` 都会整份拒绝，而静态检查只比对文本、发现不了这种分叉）；同一份数据导出两次逐字节相同；整体替换真的是「先删后插」而不是合并；**豁免不泄漏**到 RPC 之外的事务；坏 payload 被拒且一条都不写；两个云端账号之间 RLS 隔离有效（互相看不到、冒用 `user_id` 被拒、B 的替换不牵连 A）；未登录调用拿不到任何数据。它**不证明** PostgREST 的 schema cache、GoTrue 的会话与 Supabase 的托管配置——那些只有真实项目能验（`docs/19` §5 的 S6）。

`npm run icons` 用本机 Chrome 无头模式把 `public/favicon.svg` 渲染成 192 / 512 / maskable 512 / apple-touch-icon 180 四张 PNG（不引入任何图像处理依赖），产物提交在 `public/` 下，脚本可重复执行。

## 验收步骤

1. 注册或登录后在"准备明天"完成五项准备（含补剂）、三餐（多选食物 + 备注）、晨间、健身（多选项目 + 备注）和自定义事项；刷新确认从本地数据库恢复。
2. 在"执行今天"确认完成勾选独立于准备状态；补剂和健身可逐项勾选执行；日期标题两侧按钮可查看其他日期。
3. 使用"复制昨天"，确认计划内容（含食物/补剂/健身快照）被复制、五项准备和全部完成状态未复制，且目标日期模式与 `mode_override` 未改变。
4. 使用两个本地账号验证各自的三餐、自定义事项、补剂和选项（食物 / 补剂 / 健身）相互不可见；尝试新增、修改、删除历史从属记录必须被服务层拒绝。
5. 切到明天或更远的日期（尚未规划时）应看到「这一天还没有计划」引导块；勾选任意准备项或保存任一面板后，该引导自行消失。昨天及更早的日期只显示「历史计划仅供查看」，没有编辑入口。
6. 进入「选项」：新账号应已带出示例食物 / 补剂 / 健身项目；补剂按早 / 中 / 晚分组。尝试新增重名项应被拒绝且面板保留输入；停用与删除都需要二次确认，停用项仍留在清单里并把「启用 N 项」计数减一；刷新后清单、顺序与停用状态不变。
7. 打开补剂面板：应自动从模板生成当日实例（早/中/晚），模板来源的行不可删除；可添加自定义补剂行并可移除；保存后刷新确认实例与完成状态正确恢复。
8. 切到周六或周日（正常休息日）：应自动出现「拖地」「洗衣」两项且仅需勾选完成；没有衣服/三餐/晨间准备项；补剂、健身和自定义事项仍可用。工作日手动切到休息日（临时不上班）：不出现拖地/洗衣，显示「临时不上班」说明；恢复默认后家务重新出现。
9. 从日程页右上角进入「选项」，打开其中的「本地数据备份」：点「生成备份」应得到带格式标记与来源账号的 JSON 文本；改几条数据后再粘贴原备份、点「检查这份备份」会列出备份内容与来源账号并需二次确认，确认后当前账号数据被整体替换、改动的数据回退；刷新后确认还原结果仍在。
10. 在同一个卡片里粘贴一段非法文本（比如随便打几个字），点「检查这份备份」不应弹确认框，而是给出可读错误且现有数据分毫不动；输入为空时「检查这份备份」按钮应处于禁用状态。
11. 备份也是唯一的「换设备」路径：在浏览器里清空本站点数据（等同换台设备），重新注册一个新账号，应拿到全新示例选项而不是旧账号残留；把之前导出的备份粘进卡片导入，选项清单与日计划内容（含准备项、三餐快照）应完整回到这个新账号下。
12. 从日程页右上角进入「选项」的「存储与安装」：应看到本地存储用量、持久化存储是否已获得、运行方式是否独立窗口三项真实状态。桌面浏览器上是「浏览器标签页」，从主屏幕图标打开时是「独立窗口（已安装到主屏幕）」并显示「已经安装」。
13. 移动端（**必须真机**，桌面浏览器验不了）：用 `npm run build` 的产物部署到 HTTPS 地址后，在 iOS Safari 里点分享 → 添加到主屏幕，再从主屏幕图标打开——应没有浏览器地址栏、`display-mode: standalone` 为真，且「存储与安装」显示「独立窗口（已安装到主屏幕）」。底部导航不应被 Home 指示条盖住（安全区已在 `verify:pwa` 里用 CDP 模拟验收，真机只需确认观感）。这一条的目的是让本地数据进入独立存储分区，避开 iOS「7 天无交互即清空可写存储」的规则；**安装不能替代备份**，重要数据仍要用上面的导出留一份。
14. Android Chrome 上若浏览器给出了安装入口，「存储与安装」里会出现「安装到主屏幕」按钮，点击应触发系统安装流程。
