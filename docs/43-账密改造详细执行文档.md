## 1. 目标与范围

用户确认将现有账号体系改成常规的账号密码登录：应用界面仅使用「账号」和「密码」，正式环境最终只保留一个可用账号。

| 项目 | 目标 |
| --- | --- |
| 展示账号 | `W` |
| 账号归一化 | 输入去除首尾空白并转小写，内部标识为 `w`；`W` 与 `w` 视为同一账号 |
| 初始密码 | 使用用户指定值，由可信管理入口设置；不保存在版本库，密码不做 trim 或大小写转换 |
| 认证来源 | Supabase Auth 是账号密码认证的唯一来源；本地资料与离线缓存不构成第二套认证 |
| 数据归属 | 以同一个 Supabase 用户 UID 关联账号资料、本地业务数据、云端业务数据和待上传状态 |
| 登录行为 | 退出后可用原账号重新登录；本地缓存被清除或换设备后仍可认证并恢复已上传的数据 |
| 账号入口 | 移除公开注册和二次云端绑定入口；服务端也限制为保留的 UID |
| 本地写入 | IndexedDB 恒为业务唯一写入落点，云端业务通道负责上传与整体替换 |

用户指定的初始密码属于弱密码。上线时一次性通过可信管理入口设置，不写入版本库、应用源码、构建环境变量、种子数据或前端比较逻辑，也不在应用启动时自动创建账号。若真实 Auth 密码策略拒绝该密码，明确记录阻塞，不能自动降低全项目策略或换一个密码后声称满足需求。

“清除所有现有的账号名”在本方案中指清理运行中的旧账号身份、旧登录入口和活动资料，最终生产仅保留 `W`。Git 历史、历史文档和受保护的迁移备份属于恢复证据，不通过删除这些内容来代替账号清理。

账号清理与业务数据清空必须分别处理。用户已提出只保留 `W`；旧账号下的日程、选项及未上传编辑是否迁给 `W`，需要先给出盘点结果与具体去向。默认在去向明确前保留备份并隔离，不顺带删除业务数据。

## 3. 改造前实现与原因分析

### 3.1 改造前登录链路

```text
账号 + 密码
  -> 本地 users 查找账号并比对本地 password_hash
  -> localStorage 写入本地随机 UUID 会话
  -> 本地登录成功
  -> 尝试用同名合成邮箱登录 Supabase
  -> 将 Supabase UID 侧挂到本地账号的 sync_state
  -> 云端失败仍允许进入本地业务页面
```

改造前不是一个由云端账号统一认证的系统，而是本地账号与云端账号并存。下表记录基线提交 `b646e6af9ea5bcacece0da90ef5e7532a619b261` 中的行为，不代表现在的源码；同名文件已按新方案修改，旧 `accountLink.ts` 已移除：

| 源码 | 已确认行为 | 对目标的影响 |
| --- | --- | --- |
| [本地认证](../src/services/local/authService.ts) | `users` 保存随机 UUID、账号名和自制 `local-*` 密码哈希；登录扫描本地记录 | 同一个云端账号在新浏览器没有本地记录时不能直接登录 |
| [认证门面](../src/services/api/authService.ts) | 先本地登录/注册，再尽力绑定/创建云端身份；云端失败仍返回本地成功 | 本地成功不证明云端账号存在或认证成功 |
| [会话存储](../src/services/session.ts) | 会话 JSON 存在 `happy-little-molly.session`，仅包含用户 ID 与账号名 | 不是经过 Auth 验证的身份凭据，也没有 token 生命周期 |
| [应用入口](../src/app/App.tsx) | 启动只恢复本地会话，监听本窗口事件 | 云端会话过期、刷新和跨标签退出未统一协调 |
| [云端 SDK](../src/services/cloud/supabase.ts) | 已配置会话持久化与自动刷新 | SDK 能力存在，但应用身份仍由本地记录决定 |
| `src/services/sync/accountLink.ts`（历史路径，现已移除） | 自动绑定读取云端摘要与本地条数后丢弃结果，直接启用上传 | 没有完整处理双方已有数据的冲突与恢复 |
| [本地退出](../src/services/local/authService.ts) | 只清应用会话，不退出 Supabase 会话 | 退出的实际状态分为两套，易出现残留云端会话 |
| [上传映射](../src/services/sync/mapper.ts) | 推送时将四张根表的本地 `user_id` 替换为云端 UID | 本地 UUID 与云端 UID 本来就不是同一个身份 |

本地密码哈希是无盐的简单确定性哈希，不能作为常规公网认证方案，也不能把 `local-*` 值直接导入 Supabase 的密码存储。

### 3.2 已知问题与尚未确认的故障

从源码可以确认：本地用户记录丢失或换 origin/浏览器时，即使云端账号存在，本地登录路径也无法直接使用它。云端注册曾失败则会留下仅在原浏览器可用的本地账号，但该失败本身不应阻止完整本地账号重复登录。重新注册会产生另一个本地 UUID，其下查询不到旧 UID 所属的数据，并不等于旧数据已经删除。

但本轮尚未在用户实际失败设备复现“只能登录一次”。按改造前代码，本地账号记录和原密码完整保留时应能重复本地登录。不能直接断言是哪一个存储被清除、哪个云端配置报错，或说原因已经完全定位。

[Service Worker](../public/sw.js) 主要处理同源静态 GET 缓存和旧 Cache Storage 清理，跨域请求绕过。现有代码没有在退出或更新时清空 IndexedDB/localStorage。PWA 缓存、认证会话和业务数据库必须分开调查。

生产切换前仍需核实：

1. 失败设备的访问地址、浏览器/PWA 类型、是否换域名或端口、是否清过网站数据。
2. 首次注册和重新登录各自的实际错误、HTTP 状态及 Supabase Auth 错误码；采集时不记录密码或完整 token。
3. 故障时本地 `users`、会话镜像、云端会话是否存在，以及各自 UID 是否匹配。
4. 真实项目 Auth 用户、邮箱确认、密码策略、项目暂停状态、构建时配置是否指向同一项目。
5. Supabase Auth 日志及安全/性能 advisories。真实项目尚未在本轮读取，不能把官方文档搜索当成线上核验。

## 4. 架构决策与现行规则的变更

### 4.1 保留的约束

- `DATA_BACKEND` 继续为常量 `'local'`。业务写入、离线编辑和待上传队列仍在 IndexedDB。
- 界面只引用 `services/api/` 门面；认证、同步和底层存储细节不进入 React 页面。
- Supabase 环境变量仅在 `services/capabilities.ts` 读取；认证门面通过动态 import 进入编排层。
- `services/cloud/` 保留 `errors`、`identity`、`rpc`、`supabase` 四个传输模块，不恢复云端业务 Service 副本。
- IndexedDB 与 SQL 迁移只追加；不修改已经发布的历史迁移来伪装兼容。
- 本地保存、认证成功、上传成功、恢复完成分别表述。队列为空不宣称「已同步」。
- 整体替换继续明确哪一端被替换、数据损失范围和「不可撤销」。
- 全局上传调度器仍在 `main.tsx` 接线，不能挪进 React effect。
- 不新增 `public/_redirects`；保留现有 SPA 回退与 PWA 缓存纪律。

### 4.2 被新方向取代的旧规则

| 旧设计 | 新设计 | 实施时需要同步更新 |
| --- | --- | --- |
| D5：本地账号是应用身份，云端账号侧挂 | Supabase UID 是统一身份，本地仅缓存该身份的资料与业务数据 | 认证/会话代码、架构断言、活文档 |
| 未配置云端仍可本地注册和密码登录 | 首次登录与重新输入密码登录需要配置并连接 Auth | 能力状态、配置失败提示、测试夹具 |
| 登录成功后云端失败仍视为登录成功 | 密码认证失败不能创建本地成功会话 | `AuthResult`、事件、页面提示 |
| 手动“连接另一个云端账号” | 当前账号的云端身份与本地身份一致 | 设置页、绑定接口、同步状态 |
| 换设备先注册本地账号再导入 | 登录同一个账号后恢复该 UID 的数据 | 引导、备份说明、真机验收 |
| 一期完全不自动下载 | 新设备/空工作区认证后必须先恢复云端数据 | 启动状态机、恢复规则、测试 |

这里改变的是身份来源与首次恢复流程，不将业务读写直接改成云端。未配置 Auth 的构建应如实显示不可登录及配置原因，不能继续偷偷创建本地账号。开发和验收采用隔离的假 Auth 或测试项目，不把测试放行分支带进生产。

实施时更新 `README.md`、`HANDOFF.md`、`docs/19-sync-execution-plan.md` 的当前执行状态及相关代码注释、静态断言。历史完成报告保留原文，注明新方案接替的规则即可。

## 5. 账号 W 与身份准备

### 5.1 对外账号与内部登录标识

Supabase `signInWithPassword` 支持 email/phone，不原生接受 username。界面仍只呈现账号与密码，由 `cloud/identity.ts` 将规范账号映射到稳定内部标识。

当前实现仅接受规范账号 `w`，固定内部标识为 `w@molly.local`；不是继续支持任意 `<username>@molly.local`。`W`/`w` 只是同一输入规则与展示资料，不决定实际权限。生产切换前必须核实真实项目中的目标账号、内部邮箱、Auth UID 及数据；能保留合法目标 UID 时优先保留，不能按旧账号名猜 UID，也不能因为改展示字段而另建身份导致原数据失联。

本期固定单账号不需要立即建设通用的账号名查询服务。若未来开放多账号，再单独设计用户名唯一约束与解析服务，不能依赖客户端可编辑 `user_metadata` 决定访问权限。

合成邮箱无法接收验证或重置邮件。本期由可信管理入口协助恢复密码，不展示实际不可用的邮件找回流程；新账号需通过管理员准备为可直接认证状态，不默认关闭整个项目的邮箱安全设置。

### 5.2 一次性准备与服务端限制

按仓库部署规则，平台登录、Auth 控制台配置及账号一次性准备由用户在可信入口完成；代理不索取 `service_role`，不把管理员能力或初始密码下发前端。数据库迁移和部署另按现有授权与凭据执行。

执行记录只保留目标 UID、内部标识及准备结果，不保存密码/refresh token。检查以下条件：

- `W` 的身份唯一，用户能实际以指定密码登录；原目标 UID 可复用时不重复创建。
- 关闭公共 signup，并停用本产品不需要的匿名、社交和其他身份入口。
- 服务端按保留 UID 或受保护 allowlist 限制业务访问；仅隐藏注册按钮或前端拒绝旧账号不够。
- 门禁覆盖所有根表、子表、资料、诊断表及 RPC 可达路径。默认拒绝未授权 UID。
- RLS 保留 `auth.uid()` 所有权检查，UPDATE 同时具备 `USING` 与 `WITH CHECK`。
- 不用 `user_metadata` 授权；不为解决权限问题随意增加 `SECURITY DEFINER`。

当前第七迁移中的四个公开 RPC `account_access`、`cloud_sync_summary`、`export_cloud_snapshot`、`import_local_backup` 均为 `security invoker`。唯一受限的 `security definer` 查询是私有 `private.is_account_allowed()`：不接受调用者指定的 UID，只读取当前 `auth.uid()` 是否在私有 allowlist，不读取业务数据，也不提供修改 allowlist 的能力。

旧账号先停止业务访问、处理会话，再在数据保全完成后删除。删除 Auth 用户不会让已经签发的 JWT 立即失效；严格限制需服务端 UID 门禁，必要时核实 `session_id`。撤销 refresh session 与等待 access token 到期不能互相混淆。

## 6. 目标认证与启动流程

认证编排已落在 `services/sync/authSession.ts`，所有界面订阅与操作经 `api/authService.ts` 导出。`cloud/` 仍保留四个传输模块。

### 6.1 状态与读写权限

| 状态 | 页面行为 | 本地业务写入 | 云端上传 |
| --- | --- | --- | --- |
| `checking` | 等待配置、SDK 会话与工作区检查 | 禁止 | 禁止 |
| `signed-out` | 账号密码登录页 | 禁止 | 禁止 |
| `preparing` | 认证成功，准备或恢复该 UID 数据 | 普通编辑禁止 | 禁止 |
| `ready` | 当前 UID 的业务工作区 | 允许 | 按真实认证与队列状态允许 |
| `offline-cached` | 已建立过的该 UID 本地工作区 | 允许，变更保留待上传 | 禁止 |
| `reauth-required` | 身份失效，要求原账号重新登录 | 默认禁止；保留数据与队列 | 禁止 |
| `error` | 显示实际配置/恢复错误并可重试 | 禁止 | 禁止 |

`offline-cached` 是复用之前成功认证并完成准备的本地工作区，不是在离线时用自制密码验证“登录成功”。首次登录、主动退出后以及明确获知 token 被撤销后，不允许通过旧会话 JSON 重新进入。

离线期间无法即时知道服务端是否撤销身份，这是本地优先的边界。恢复网络后必须重新验证身份再上传；若校验拒绝，保留未上传编辑并进入重新认证状态。

### 6.2 生命周期顺序

1. 启动认证编排并注册 Auth 事件；上传单例可初始化监听，但受 readiness gate 控制。
2. 读取 SDK 持久会话。线上恢复用 `getUser()` 验证身份，不把读取本地 token 的 `getSession()` 视为服务端认证。
3. 判断保留 UID 与身份代次，打开该 UID 工作区；旧本地镜像仅作迁移线索。
4. 完成工作区与队列检查、云端首次恢复；旧随机 owner 数据默认隔离，不按账号名自动认领。
5. 再检查 SDK 当前 UID 未变化，发布 ready context，挂载业务页面；最后才允许自动建计划和上传。新工作区不自动播种示例选项。

监听 `INITIAL_SESSION`、`SIGNED_IN`、`SIGNED_OUT`、`TOKEN_REFRESHED`、`USER_UPDATED`。Auth 回调保持同步，异步 SDK/数据库编排延后执行，避免在回调中 await SDK 导致死锁。

`currentUser()` 可保持同步接口以控制改动范围，但值应来自已准备的运行时上下文，而非任意 localStorage JSON。session mirror 不含密码或额外 token 副本；SDK 自己管理会话持久化。

### 6.3 退出、重新登录与并发

普通退出明确使用 Supabase `signOut({ scope: 'local' })`，避免默认 global 退出踢掉其他设备。按实际 SDK 结果报告退出状态，同时封闭本机工作区、停止新上传、清理应用运行时会话；离线或服务端退出失败路径需验证不能自动恢复已主动退出的会话。

普通退出保留本地业务记录及未上传队列。改造前“断开云端连接并清队列”的流程已移除，不能作为普通退出的实现。同账号重新认证后按 UID 打开原工作区，再恢复上传。

每次业务/上传/导入任务捕获 `{ ownerUid, generation }`。身份变化时增加 generation；每个长 await 后及提交前检查上下文仍有效。旧请求可能已经提交云端，不能承诺退出撤销已发生请求，但其完成回调不能写入新工作区或错误清掉新队列。

跨标签页通过 SDK/storage 通知协调，增量上传与整体替换共用 Web Lock。业务页面按 UID 与有效工作区代次重置状态，`useDayPlanData.ts` 和选项 hooks 的异步成功、失败与自动写入均检查上下文。

已补认证事件序号与准备完成前 SDK UID 复核：迟到 `SIGNED_OUT` 先读取实际 SDK 会话，不关闭仍有效的新会话。SDK 自身跨标签 logout 仍可能移除共享的新会话；此时如实关闭工作区并要求重新登录，不伪造 `ready`。本次没有另行扩展 SDK 跨标签认证锁。

## 7. 数据归属与迁移设计

### 7.1 需要统一的所有权

| 数据 | 改造前归属 | 改造后归属/处理 |
| --- | --- | --- |
| `users` | 本地随机 UUID、账号、密码哈希 | 活动表仅缓存 Auth UID 与 W 的资料；旧资料去掉密码后放入 `legacy_users` |
| `day_plans` | 本地 `user_id` | Supabase UID |
| `food_options`、`supplement_templates`、`exercise_options` | 本地 `user_id` | Supabase UID |
| 六张业务子表 | 沿 plan/meal 父键归属 | 延续父键归属并验证关联完整性 |
| `sync_state.id` | 本地 UUID | 同一 Supabase UID |
| `sync_outbox.local_user_id` | 本地 UUID | 保留现有字段名，其值固定为当前 Supabase UID；旧队列放入 `legacy_outbox` |
| 云端根表 | Supabase UID | 保留，按需要迁移旧用户数据到目标 UID |
| `device_id` | 设备标识 | 保持设备语义，不当账号 ID |

六张子表是 `daily_meals`、`daily_meal_items`、`daily_supplements`、`daily_exercise_items`、`custom_tasks`、`routine_tasks`。它们不因统一 UID 被全部新增 `user_id`；沿完整父链判断所有权，同时在本地服务通过 parent ID 修改记录时检查 parent 属于当前 owner。

云端 `profiles` 目前只有 user_id 与时间字段，没有可直接复用的 username 字段。是否新增显示资料字段应以需求决定，不能把 Auth 密码放进 profiles。

### 7.2 盘点与业务备份

实施前建立不含密码/token 的清单：设备、origin、PWA 安装环境、本地账号 ID、历史云端绑定 UID、各表条数、历史日期范围、队列数量及故障证据。不同 origin/浏览器的数据不能通过一次前端升级全局清理，每个设备要单独跟踪。

备份分三类：

1. 每个旧工作区的业务导出，包含完整父子关系与名称快照；不能登录的旧数据需可信只读救援导出，不能为此重新注册。
2. 受保护的本机恢复快照，含结构版本与设备/队列状态；不用它作为通用可共享业务备份。
3. 云端业务与 Auth 管理清单及恢复措施；普通业务 JSON 不包含可恢复的 Auth 密码。

对每份备份记录时间、来源、表计数和文件校验值，并在隔离环境实际导入核对。敏感恢复快照放在受保护且忽略的目录，不因本次 Git 版本保存而提交真实账号数据库、token 或密钥。

### 7.3 映射与冲突方案

建立明确映射：`旧本地 UID -> 旧云端 UID（如存在）-> W 的目标 UID -> 数据处置`。不能靠账号名相同、设备当前 session 或“只剩一个账号”猜测归属。

每个数据集的处置为迁入 W、仅备份后隔离或明确删除。迁入多份数据时预检查同日期计划唯一索引、全局记录 ID、重复选项及跨 owner 引用；不能静默选择一个同日计划或直接 last-write-wins 合并。

当前上传是“增量上传 + 手动整体替换”，不是自动双向合并。将 UID 统一不会消除多设备同日不同 ID 的唯一冲突、旧数据覆盖或删除记录复活。迁移期间指定一个主设备，其他设备暂停编辑/上传；新设备先恢复同一份云端记录 ID 后启用编辑。正式多设备并发编辑需另做版本/冲突和删除墓碑设计，在完成前如实说明能力边界。

### 7.4 IndexedDB 升级与幂等执行

本次追加 v8 升级，当前 `DB_VERSION = 8`，共 18 个仓库。新增 `legacy_users`、`legacy_outbox`、`legacy_sync_state`、`workspace_state`、`workspace_migrations`；旧迁移保持原样。

结构升级与认证后 owner 搬迁分开执行。`versionchange` 事务不 await 网络/Auth。v8 将旧身份、旧队列和绑定状态隔离，旧业务图留在原 owner 下。目标 UID 经验证且迁移映射确定后才可显式复制旧工作区。

每个 origin 的执行顺序：

1. 拦住旧 UI 写入、调度器和其他标签页，确认备份已验证。
2. 全量预检查关联、日期唯一约束、记录 ID 冲突及旧 owner 范围，生成不含密码的迁移预览。
3. 若明确选择迁入，在一个本地 readwrite 事务内复制完整业务图、重映射全部 ID 与关联、写入目标资料和 journal，使用 `track:false`。原业务和旧队列保留，不把未经核验的旧上传意图转为活动队列。
4. 本地迁移完成不代表云端上传完成。按目标云端现状进行选定的恢复、替换或迁移上传，记录独立阶段。
5. 核对条数、日期、名称快照、完成状态、队列及 owner，再开放工作区。

`workspace_state` 持久记录该 UID 的初始化来源和时间。`workspace_migrations` 在复制事务内记录源/目标 UID、条数、开始和完成时间，源 owner 唯一索引保证重试不重复复制。真实迁入前还须在受保护的操作记录中保存备份引用与核验结果；本次未迁入用户实际数据。

旧密码哈希不作为 Supabase credential。v8 结构升级时即隔离旧身份、清空活动 `users` 并移除旧账号名唯一索引；隔离资料也不保留密码或身份 token，不等待业务复制完成才去除凭据。活动 `users` 只缓存已验证的 Auth UID 与展示账号 W 的资料；需保留的旧业务数据继续隔离或保存在已验证备份中，不能成为仍能认证的隐藏账号。

### 7.5 备份与云端恢复兼容

改造前业务备份为 v2。当前格式为 v3，导出仅包含业务图与资料缓存，不含密码/token。继续只读兼容 v1/v2，并去掉旧 `users.password_hash`；导入不创建账号，根表 owner 取当前认证 UID。

新增 SQL 迁移中的 `export_cloud_snapshot` 同步输出 v3/DB v8。快照资料 UID、字段、条数、完整父链与来源选项归属验证通过后才准备工作区；来源选项必须属于同一 owner，名称快照不能掩盖跨 owner 引用。首次空快照可初始化，手动整体恢复不会用空快照清空本地。

普通导入保留记录 ID，在同一事务内拒绝与其他 owner 或孤儿记录的同表主键冲突。同时检查所有保留记录的父/来源引用：若导入会补齐其缺失的计划、餐次、食物或运动来源记录，使原本隔离的记录重新接入当前账号，整次拒绝且不写入；不能只验证 incoming 图而忽略库中的残留记录。当前 owner 将被整体替换的旧记录不作为其他工作区的保留记录处理。

显式复制旧工作区对十张业务表的完整关联图生成新 ID，同步重映射五条计划子表引用、餐次父键及 food/exercise 来源选项。新 ID 必须避开已有主键和所有有效父/来源引用值，防止碰巧填上孤儿引用；`null` 来源保持为空，根表 `user_id` 是账号身份而不是业务记录引用。缺失的旧来源选项可在只读快照中转为 `null` 并保留名称，不改动原记录。复制后再检查完整父链、来源 owner 和冲突，不能只修改根表 ID。

恢复业务数据、清理当前 UID 队列、写入工作区与恢复状态在同一个事务提交；身份变化立即使事务 guard 失效。整体上传只退役快照捕获的队列 ID，上传中的新编辑继续保留。

### 7.6 云端旧数据迁入 W

仅当盘点表确认需要保留旧云端业务数据时执行迁入。跨 Auth UID 的搬迁不通过匿名前端或普通账号绕过 RLS；使用已授权的数据库连接在可信执行环境完成专用迁移，不新增供所有客户端调用的提权搬迁 RPC。

1. 暂停相关设备上传，确认目标 Auth 用户已存在，保存源/目标云端备份与表计数。
2. 检查源/目标同日期计划、全局 ID、选项引用、历史日期触发器和现有 RLS；准备完整关联图及冲突预览。
3. 在事务内按批准的方案迁移四张根表 owner；需要重映射 ID 或处理同日冲突时同步更新所有父子键和选项引用。不要删除再创建 Auth 用户来实现改名。
4. 本地设备沿用同一份记录 ID 映射，防止旧待上传项再次插回被废弃的记录。迁移队列保留有效意图，对无法证明有效的旧 delete/upsert 先隔离，不直接回放。
5. 核对源/目标条数、完整关联、历史状态与 RLS；记录云端迁移完成阶段，再开放目标 UID 的业务访问与主设备上传。
6. 检查旧 Auth UID 下还有无未处置业务数据；清理旧身份之前再次确认删除所触发的级联范围。

现有业务根表引用 `auth.users(id)` 且配置 `ON DELETE CASCADE`。删除旧 Auth 用户会级联删除其仍拥有的业务数据；必须先完成迁移或保全，不能先删除账号再从空表验证“旧账号已经清干净”。若选定方案是保留旧数据备份后删除，也要独立记录相应数据损失和可恢复范围。

## 8. 首次恢复与上传保护

| 本地与云端状态 | 处理 |
| --- | --- |
| 本地未初始化，云端有数据 | 先恢复快照、验证 owner 和关联，再开放业务；不先播种示例 |
| 本地未初始化，云端明确为空 | 完成空工作区标记后按现有规则初始化一次 |
| 云端请求失败/权限错误 | 显示错误并可重试，不能当成空数据或上传空快照 |
| 本地已有数据，存在待上传编辑 | 保留本地与队列；认证恢复后按既定队列策略处理，不能自动云端覆盖 |
| 本地/云端都非空且来源冲突 | 显示实际预览并执行选定方案，未决定前停止上传/替换 |
| 已准备工作区暂时断网 | 可进入该 UID 的离线缓存，编辑入队，联网验证后补传 |
| 本地缓存被清除 | 可认证并恢复云端已有内容；未上传且已被清除的编辑无法凭账号找回 |

上传每轮固定 owner/generation，验证 SDK 当前 UID 与本地工作区一致。取批次、主表读取、delete/upsert、出队、失败次数及 `sync_state` 更新均使用同一个上下文，不能在中间重读“现在用户是谁”后写给另一身份。

保留现有推送纪律：读取主表最新行，delete 优先，依赖排序后截断，整批失败如实记录。只有业务准备完成且网络身份有效才能放行。新登录、token 刷新和工作区 ready 需要触发调度，不能只依赖写入或 online 事件。

- 读取真实项目日志和 advisories，核实 schema、Auth 用户、RLS/GRANT/RPC、构建配置及会话生命周期。
- 查明保留 UID/internal identifier，记录旧账号数与每个账号数据，不导出密码/token。
- 在隔离环境构建对应失败场景，区分本地记录缺失、云端失败、token 失效和恢复缺失。

### P1-P2 具体步骤

- 给出每个旧数据集的迁入/隔离/删除预览，完成关联校验和恢复演练。
- 用户可信准备 W，验证密码策略与登录结果；保留目标既有 UID。
- 在测试项目关闭 signup，并验证直接调用 Auth signup 也被拒绝。
- 审核 UID 门禁全部可达路径，新增最小授权与 RLS，不把前端 allowlist 当服务端保障。

### P3-P6 具体步骤

- 先调整状态与门面契约，再接入 SDK 生命周期；当前静态断言随决策一起更新，保留数据层边界。
- 增加本地升级和幂等迁移，再加入首次 hydrate、队列保护与过期异步结果防护。
- 删除活动本地注册/密码校验、自动云端注册与二次绑定链路；不能只隐藏按钮。
- UI 收口后逐项核查登录、退出、备份、断网和失败文案；按实际结果显示上传/恢复状态。

### P8 具体步骤

- 保持域名/origin，先准备服务端兼容变更和新构建，再按窗口暂停旧写入并启用门禁。
- 主设备先迁移核对；其他设备更新 PWA 后按清单恢复/迁移，避免旧缓存构建继续创建本地账号。
- 未完成更新的离线设备可继续持有旧缓存，不能宣称已经远程清除了它们；联网后旧身份访问应被服务端拒绝。
- 确认所有旧账号业务数据已迁移或可恢复，再处理会话、删除旧 Auth 用户和活动本地旧资料。
- 删除操作按清单精确定位，不用全表清空或全站存储清除作为迁移捷径。

### 11.2 必须覆盖的行为

| 场景 | 验收标准 |
| --- | --- |
| `W`/`w` 与指定密码 | 均进入同一个 UID；输入无凭据泄露 |
| 错密码、旧账号、未知账号 | 明确失败，不创建账号/本地成功会话，原数据不受影响 |
| 单字符账号 | W 不再被现有 3-20 位注册规则误拦 |
| 密码精确比较 | 测试密码后加空格等不同输入不能被前端 trim 成合法密码 |
| 连续退出重登 | 多次成功，账号 UID、业务记录、待上传队列保持正确 |
| 普通退出 | 本机工作区关闭，不误踢其他设备，不删除本地数据/队列 |
| 刷新、关闭重开、后台返回 | 正确恢复/刷新会话，不靠旧 JSON 伪认证 |
| token 过期或撤销 | 可按状态刷新或要求重新认证，不能换成新本地 UUID |
| 网络失败与 Auth 拒绝 | 分别处理，网络失败不能被认作账号不存在或云端为空 |
| 无 Auth 配置 | 显示配置原因，不能本地注册绕过 |
| 新设备或清缓存 | 原账号可登录，先恢复云端记录，再启用自动创建/上传 |
| 未上传编辑 | 断网、退出、认证过期及重登后保留；不会被 hydrate 覆盖 |
| 旧库迁移 | 代表性历史库版本、旧邮箱账号、多 UID、孤儿/冲突记录均有明确结果 |
| 中断与重试 | 结构升级、owner 搬迁、云端准备任一阶段中断后可续跑，无重复数据或丢队列 |
| 旧备份与相同 ID | v1/v2 兼容；普通导入拒绝跨 owner/孤儿同表主键冲突，显式复制全图换 ID；失败零写入 |
| 残留父/来源引用 | 导入不得因补齐缺失父/来源而认领保留的孤儿或其他 owner 记录；复制 ID 避开全部有效引用 |
| 多标签与 in-flight 退出 | 旧结果不能写新工作区、错清队列或错写 sync_state |
| RLS 隔离 | 测试账号 B 看不到/改不了 A 的根表、子表、资料与 RPC 数据 |
| signup 与旧 JWT | 直接接口不能注册；旧身份已签发 token 也不能绕过 UID 门禁 |
| 文案 | 认证、本地保存、上传、整体替换、失败的说明与事实一致 |
| 手机 PWA | 安装环境重启/断网/更新/重登通过，静态资源不被 HTML rewrite |

不同 UID 的 RLS 和并发测试使用隔离测试项目的临时账号，测试后清理。生产只有 W 不构成跳过隔离测试的理由，不往生产临时新增第二个可用账号。

测试日期显式选择工作日/休息日，不假设验收当天是工作日。新账号是否为空、是否有示例数据以及周末自动建计划，均在 fixture 中明确。

## 12. 发布、回退与停点

### 12.1 发布准备

执行者先读 [已更新的部署说明](27-deploy-runbook-for-codex.md)，结合本文和第 44 份文档执行统一 Auth UID 方案。历史“未配云端仍可本地账号登录”的产品规则已被取代。不重新执行所有历史迁移；核实真实 migration history，只部署缺失且已验证的迁移。

`VITE_*` 是构建期变量，先设置目标环境再构建/部署；只用现有 anon key，不将管理员凭据放进前端。新表需核实 Data API 暴露设置、最小 GRANT 与 RLS；新增 RPC 核实 EXECUTE 授权、身份门禁并刷新 schema cache。

PWA 保持 `/sw.js`、manifest 与入口的 no-cache，带哈希 assets 长缓存；上线后核实首页、深链接、JS/SW 内容类型和缓存头。部署 URL 可访问不等于认证与恢复验收通过。

### 12.2 回退

- 源码可从 `账密改造前版本` 新建隔离分支/工作区取回，不使用 `git reset --hard` 覆盖用户当前文件。
- 数据恢复使用对应设备/云端的迁移前备份及 journal，在隔离环境先核对恢复范围。
- IndexedDB 升级后不能假设旧 DB_VERSION 构建能打开；旧程序直接连接新库可能出现 VersionError 或旧归属语义错误。
- 新服务端门禁与旧认证模型不兼容时，不能只发布旧前端。需要整套兼容方案，或部署修复版本。
- 已删除 Auth 用户的 UID/凭据不能靠普通业务 JSON 恢复；因此“先隔离、后删除”是最终清理的前置条件。
- 回退保留未上传编辑，独立说明哪些内容已上传、哪些需要人工恢复。不能承诺 Git 标签可恢复整个线上系统。

### 12.3 停止依赖操作的条件

| 条件 | 处理 |
| --- | --- |
| 故障环境/目标 Supabase 项目不明确 | 继续只读核验，不迁移或删账号 |
| W 的目标 UID 不确定或出现多个候选 | 完成账号与数据映射后再改 owner |
| 初始密码被真实策略拒绝 | 报告实际错误，等待密码/策略决策，不前端绕过 |
| 旧业务数据去向不明确 | 先备份和预览，停止相关删除/覆盖 |
| 备份校验或恢复演练失败 | 停止清理，修复备份路径 |
| ID/同日期冲突未处理 | 停止该数据集写入，给出冲突预览 |
| RLS 或旧 JWT 门禁未通过 | 不开放上线，不删除旧账号以掩盖授权漏洞 |
| 云端恢复失败 | 不初始化假空云端，不上传空工作区 |
| 真实 Auth/PWA 或必需验收未完成 | 如实列未验证项，不宣称交付完成 |
