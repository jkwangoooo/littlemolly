# 幸福小Molly：跨业务反馈编排架构改造方案

> 状态：第二阶段进行中（礼花、宠物表现和普通完成提示已由 FeedbackHost 承载）
> 目标：让模式切换、礼花、玻璃文案、宠物回应和保存错误通过统一的反馈编排层协作，避免业务页面直接互相调用。

## 1. 背景与问题

当前日计划页在一次业务写入成功后，可能同时更新：

- `HolidayCelebration` 礼花/庆祝层。
- `FloatingPet` 与 `PetMessageBubble` 宠物反馈。
- `completion-feedback` 普通完成提示。
- `SaveStatusBar` 本地保存/失败状态。

这些反馈目前由 `DayPlanScreen` 直接持有多个状态并分别调用。短期可用，但随着“改为工作日”“完成事项”“云端连接”“备份导入”等动作增加，会产生以下风险：

1. 同一个动作重复播放多个反馈。
2. 写入失败时部分成功动画已经开始。
3. 切换日期后旧请求的反馈污染新日期。
4. 宠物组件需要知道越来越多的业务语义。
5. StrictMode 或重试路径导致重复消息。

## 2. 设计原则

### 2.1 业务只发布事实

业务层只在真实本地写入成功后发布领域事件，不直接调用动画组件或宠物组件。

```ts
publishFeedback({
  type: 'day-mode-changed',
  actionId,
  date,
  from: 'work',
  to: 'rest',
  relation: 'today',
  localSaved: true,
})
```

本地保存成功不等于云端同步成功，事件与文案不得越过现有本地优先规则。

### 2.2 反馈是表现，不是业务状态

礼花、宠物开心、玻璃文案、普通提示均为一次性表现。它们不能写 IndexedDB，不能改变日计划，也不能把“播放开始”当作“保存成功”。

### 2.3 统一编排

同一事件的多个表现由反馈策略决定：优先级、时序、去重、可打断性和减少动态效果均由统一层处理。

## 3. 目标分层

```text
业务动作
  ↓
本地写入成功
  ↓
DomainFeedbackEvent
  ↓
FeedbackBus / FeedbackProvider
  ↓
FeedbackHost
  ├── HolidayCelebration
  ├── PetMessageBubble / 宠物反应
  ├── InlineFeedback
  └── AccessibilityAnnouncer
```

建议目录：

```text
src/shared/feedback/
  feedbackTypes.ts
  feedbackBus.ts
  feedbackPolicy.ts
  FeedbackProvider.tsx
  FeedbackHost.tsx
  feedbackQueue.ts
```

## 4. 事件契约

第一阶段只落地模式切换事件与普通提示事件，后续再扩展。

```ts
type DomainFeedbackEvent =
  | {
      type: 'day-mode-changed'
      actionId: string
      date: string
      from: 'work' | 'rest'
      to: 'work' | 'rest'
      relation: 'today' | 'tomorrow' | 'future'
      localSaved: true
    }
  | {
      type: 'completion'
      actionId: string
      date: string
      text: string
    }
  | {
      type: 'save-failed'
      actionId: string
      scope: 'day-plan' | 'task' | 'backup'
      message: string
    }
```

`actionId` 是一次用户动作的稳定标识，用于去重。重试成功应产生新的 actionId；同一 actionId 不得二次消费。

## 5. 反馈策略

| 事件 | 反馈 | 优先级 | 是否可打断 |
| --- | --- | ---: | --- |
| `save-failed` | 错误栏与重试 | critical | 是 |
| `day-mode-changed(work→rest)` | 礼花、玻璃文案、宠物回应 | high | 用户可跳过 |
| `completion` | 完成提示、宠物鼓励 | normal | 否 |
| 云端队列状态 | 状态栏 | low | 否 |

模式切换成功的推荐时序：

```text
0ms       本地写入成功
0ms       礼花开始
350ms     玻璃文案出现
900ms     宠物局部回应
1800ms    礼花收尾
2200ms    恢复正常页面
```

失败、取消、历史日期、恢复默认、反向切换均不播放工作日转休息日庆祝。

## 6. 第一阶段实施范围

本阶段只做低风险基础设施，不改数据模型，不改云端同步，不改礼花视觉：

1. 新增类型安全的反馈总线。
2. 新增 `FeedbackProvider`，提供去重和订阅生命周期。
3. `DayPlanScreen` 通过反馈总线发布模式切换成功事件。
4. 保留现有 `HolidayCelebration` 和 `PetMessageBubble` 作为表现组件。
5. 现有失败、重试、日期失效逻辑继续由页面控制，待第二阶段统一。

## 8. 验收清单

- 只有本地写入成功后才发布模式切换事件。
- 同一 `actionId` 只发布一次。
- 切换日期后旧事件不能显示在新日期，已显示的普通提示、庆祝和宠物消息清空。
- 保存失败不触发庆祝。
- 休息日→工作日、恢复默认不触发休息日庆祝。
- 庆祝期间普通 completion 不打断礼花；普通提示有 2.1 秒自动清理。`r`n- 本地保存失败会发布一次 `save-failed` 事件，Host 只播报错误，不替代已有重试控件。`r`n- 打开选项页时清除普通提示；保存失败事件不由当前 Host 伪装消费。`r`n- 不出现“已同步”替代本地保存成功的文案。
- `npm run typecheck` 与 `npm run lint` 通过。
- 现有日期、数据、备份、同步和浏览器验收保持通过。
