# 幸福小Molly 新平台部署说明

## 目标

建立一套与旧线上环境隔离的新部署链路。旧项目保留作为回滚与数据核对依据，新项目不覆盖旧项目。

## 统一命名

| 平台 | 新资源名称 | 作用 |
| --- | --- | --- |
| GitHub | `jkwangoooo/littlemolly-platform` | 唯一代码源 |
| Vercel | `littlemolly-platform` | 主站与生产发布 |
| Cloudflare Pages | `littlemolly-platform` | 备用站与静态灾备 |
| Supabase | `littlemolly-platform` | 新后端项目 |

默认不绑定自定义域名，先使用平台分配的测试域名完成真机验收。

## 发布架构

```text
GitHub main
  ├─> Vercel production（主站）
  └─> Cloudflare Pages（备用站）

Vercel / Cloudflare Pages
  └─> 新 Supabase Project
```

本地 IndexedDB 仍然是应用的唯一写入落点；Supabase 只提供可选云端能力。前端只使用 Supabase
publishable/anon key，绝不使用 `service_role` 或 secret key。

## 需要用户完成的授权

### 1. Vercel

请在 Vercel 连接中授权当前账号访问并创建项目，至少需要：

- 创建项目
- 读取与写入项目环境变量
- 创建预览部署和生产部署
- 读取部署状态与日志

授权后不要把 Token 粘贴到聊天中。若使用 Token，放入当前终端环境变量
`VERCEL_TOKEN`，并确保 Token 属于有权创建 `littlemolly-platform` 的账号或团队。

### 2. Supabase

请授权 Supabase 连接访问并创建一个新项目，或提供一个已创建的空项目。需要：

- 创建/读取项目
- 执行数据库迁移
- 读取 Project URL 和 publishable/anon key
- 配置 Auth 的 Site URL 与 Redirect URLs

数据库迁移只会执行 `deploy/supabase-all-migrations.sql`，不会读取或修改旧项目数据。

### 3. Cloudflare

当前会话没有可用的 Cloudflare 管理连接。请连接 Cloudflare 账号，或提供以下两项到当前
运行环境变量中，不要粘贴到聊天：

- `CLOUDFLARE_ACCOUNT_ID`
- `CLOUDFLARE_API_TOKEN`

API Token 只需要 Pages 项目创建、部署和读取权限，不需要 DNS 全局编辑权限。

### 4. GitHub

GitHub 当前已连接到 `jkwangoooo` 账号。新仓库默认创建为私有仓库，除非用户明确要求公开。

## 授权完成后的执行顺序

1. 创建 GitHub 私有仓库 `jkwangoooo/littlemolly-platform`。
2. 初始化本地 Git，提交当前源码与部署配置，推送到 `main`。
3. 创建新的 Supabase 项目并执行全部迁移。
4. 验证新 Supabase：12 张表、3 个 RPC、21 条 RLS 策略，并刷新 PostgREST schema cache。
5. 配置 Auth：
   - 关闭 Confirm email；
   - 设置 Vercel 生产地址为 Site URL；
   - 将 Vercel 和 Cloudflare 地址加入 Redirect URLs。
6. 创建 Vercel 项目，配置：
   - `VITE_SUPABASE_URL`
   - `VITE_SUPABASE_ANON_KEY`
7. 创建 Cloudflare Pages 项目，配置同一组前端构建变量。
8. 执行本地验收：

```text
npm run typecheck
npm run lint
npm run build:no-empty
npm run check:dates
npm run check:local-data
npm run check:backup
npm run check:cloud-parity
npm run check:sync
npm run verify:local
npm run verify:pwa
npm run verify:sync
npm run verify:sql
```

9. 分别部署到 Vercel 和 Cloudflare Pages。
10. 对两个地址执行首页、Service Worker、manifest、静态资源缓存和深链接回退检查。
11. 用 iPhone Safari 打开 Vercel 地址验证字体、卡片字体和 PWA 交互。
12. 将最终 URL、项目 ID、迁移验证结果和回滚命令补写到本文件。

## 后续更新规则

- 修改源码后只提交到 GitHub `main`，由部署链路发布新版本。
- 数据库迁移必须先执行并验证，再发布依赖新字段的前端代码。
- 生产部署失败时保留上一版，不删除旧部署。
- Vercel 出现异常时，切换到上一个 READY 部署。
- Vercel 不可用时，用 Cloudflare Pages 备用地址进行真机测试。
- 所有 Token、数据库连接串、Supabase secret/service role key 都不得写入仓库或部署说明。

## 回滚

### Vercel

在 Vercel 项目中将上一个 `READY` 部署重新 Promote 为生产版本。

### Cloudflare Pages

在 Cloudflare Pages 项目的 Deployments 页面，将上一个成功部署重新设为当前生产版本。

### Supabase

数据库迁移只允许向前兼容。禁止通过回滚前端部署来伪装回滚数据库结构；
若迁移有问题，先停发前端，再编写经过验证的补偿迁移。
