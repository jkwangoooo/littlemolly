# 幸福小Molly最简账号密码登录执行文档

> 编写日期：2026-10-13（Asia/Shanghai）。
> 适用项目：`D:\WJKHome\小人项目包\littlemolly-main`。
> 目标：提供一个干净、可重复登录、数据按账号归属的单账号登录功能。
> 本文只定义现行最简方案；历史双身份设计与复杂部署记录仍保留在第 43、44 份文档中，供追溯使用。

## 1. 方案结论

本项目只保留一个应用账号：

| 项目 | 规定 |
| --- | --- |
| 页面显示账号 | `W` |
| 登录凭据 | 账号 + 密码 |
| Supabase Auth 标识 | 内部固定标识，由认证适配层生成，页面不展示 |
| 初始密码 | `000000`，只在可信 Auth 管理入口设置，不进入代码或文档 |
| 用户元数据 | 留空或 `{}`，不参与登录、不参与授权 |
| 数据归属 | 统一使用 Supabase Auth UID |
| 业务数据写入 | IndexedDB |
| 云端作用 | Auth 登录、按 UID 保存和恢复业务数据 |
| 注册方式 | 关闭公开注册，只保留管理员准备好的 `W` |

登录链路：

```text
用户输入 W + 密码
  -> 应用把 W 映射为固定内部 Auth 标识
  -> Supabase Auth signInWithPassword 校验
  -> 获取 Auth UID
  -> 校验该 UID 是否允许访问
  -> 打开该 UID 的本地工作区
  -> 按需恢复或上传该 UID 的云端数据
```

本方案不使用自建密码表、不在前端比较密码、不通过 `user_metadata.username` 判断权限、不新增用户名查询服务、不保留公开注册页。

## 2. 为什么采用这个方案

Supabase Auth 的密码登录接口原生使用邮箱或手机号作为认证标识，并不直接支持任意用户名。为了让用户仍然看到正常的“账号”输入框，应用只做一层固定映射：

```text
W -> 内部认证标识
```

用户不需要知道内部标识，也不需要填写邮箱。这样同时得到：

1. 页面是用户要求的普通账号密码登录。
2. 密码校验交给 Supabase Auth。
3. 退出后再次输入同样账号密码即可重新取得同一个 UID。
4. 换设备或清除浏览器缓存后，仍可以先登录，再恢复该 UID 的数据。
5. 不需要维护第二套本地密码和会话认证。

`user_metadata` 只适合保存资料，不适合做权限判断。它可以留空；账号是否能访问业务由 Auth UID 和服务端 UID 门禁决定。

## 3. 现有代码应保持的边界

### 3.1 认证

- `src/services/sync/authSession.ts` 负责 Supabase Auth 生命周期。
- `src/services/api/authService.ts` 是页面使用的认证门面。
- `src/services/cloud/identity.ts` 只负责 `W` 到内部认证标识的映射。
- Supabase SDK 使用持久会话和自动刷新。
- 登录必须调用 `signInWithPassword`。
- 登录成功后必须再次取得并核对真实用户 UID。
- 退出使用本机范围的 `signOut({ scope: 'local' })`。
- 失败必须停留在登录/错误状态，不能创建本地假登录。

### 3.2 本地数据

- IndexedDB 仍是业务唯一写入落点。
- 本地 `users` 只保留当前 Auth UID 与展示资料 `W`，不保存密码或密码哈希。
- 本地工作区、同步状态、待上传队列和业务表都以 Auth UID 作为 owner。
- 退出不删除业务数据和未上传队列。
- 重新登录同一 UID 后继续使用原工作区。

### 3.3 云端数据

- 云端业务表使用 Supabase Auth UID 关联。
- RLS 使用 `auth.uid()` 做所有权判断。
- 账号门禁只允许目标 UID。
- 子表通过父记录关系继承所有权。
- 不使用 `user_metadata`、页面输入的用户名或本地随机 UUID 做授权。

## 4. Supabase 配置步骤

### 4.1 创建或核验唯一用户

在可信 Supabase Auth 管理入口中：

1. 查找现有的目标 Auth 用户。
2. 如果已存在，保留其真实 UID，不重复创建。
3. 如果不存在，创建一个可直接登录的用户。
4. 账号对应的内部认证标识由应用固定生成。
5. 设置初始密码 `000000`。
6. `User Metadata` 留空；如果表单要求 JSON，填写 `{}`。
7. 确认用户状态允许直接密码登录。

密码只在管理入口使用一次，不写入：

- Git；
- 源码；
- `.env.local`；
- Vercel 环境变量；
- 数据库迁移；
- 测试夹具；
- 部署报告。

如果项目当前密码策略拒绝 `000000`，停止并记录实际错误；不能在前端绕过，也不能自行改成别的密码后声称完成。

### 4.2 Auth 基础设置

在 Supabase Auth 设置中确认：

- 关闭公开注册；
- 不启用本项目不需要的匿名、社交或其他登录入口；
- `Site URL` 设置为正式 HTTPS 域名；
- `Redirect URLs` 只保留正式域名和必要的本地开发地址；
- 邮箱验证策略与“管理员直接准备用户”的方式一致；
- 不为本项目增加邮件找回页面，除非后续明确需要。

### 4.3 写入 UID 门禁

完成用户创建并核验真实 UID 后，才允许写入 `private.account_allowlist`。

目标状态：

- `private.account_allowlist` 存在；
- 表中恰好一行；
- 该行 `user_id` 等于唯一 `W` 用户的真实 Auth UID；
- `anon` 与 `authenticated` 不能直接读写该表；
- 未在 allowlist 的 UID 默认拒绝访问；
- 四个应用 RPC 只能由已认证且通过 UID 门禁的用户使用。

写入后刷新 PostgREST schema cache：

```sql
notify pgrst, 'reload schema';
```

## 5. Vercel 配置步骤

### 5.1 构建变量

在 Vercel Production 先配置：

```text
VITE_SUPABASE_URL
VITE_SUPABASE_ANON_KEY
```

只允许 anon/publishable key。禁止把 `service_role` 或 secret key 放入 `VITE_*`。

变量必须在部署前配置，因为 Vite 会在构建阶段把 `VITE_*` 内联进前端产物。修改变量后必须重新部署。

### 5.2 发布顺序

1. 核对发布提交和工作区干净状态。
2. 核对 Supabase URL 与项目 ref 一致。
3. 核对 Production 两个构建变量。
4. 运行本地验收。
5. 使用现有非交互式 Vercel Token 发布。
6. 发布后核对正式域名实际指向的新部署。

不要运行交互式 `vercel login`，不要把本地无 Auth 配置的构建当作生产版本。

## 7. 生产验收清单

### 7.1 页面与静态资源

- 正式域名首页 HTTP 200；
- 任一深链接可正常打开；
- `/sw.js`、`/manifest.webmanifest`、`/index.html` 为 `no-cache`；
- `/assets/*` 使用带 hash 的长期缓存；
- Service Worker 返回 JavaScript，不被 SPA rewrite 成 HTML。

### 7.2 登录

- 输入 `W` 和正确密码可以登录；
- 输入 `w` 与正确密码行为一致；
- 错误密码被拒绝；
- 其他账号名被拒绝；
- 页面没有公开注册入口；
- `User Metadata` 为空不会影响登录；
- 真实 Auth UID 与 allowlist UID 一致。

### 7.3 会话与数据

- 刷新页面后会话可以恢复；
- 退出后再次输入 `W` 和密码可以重新登录；
- 重新登录后原工作区数据仍在；
- 新设备登录后可以恢复已上传数据；
- 清除浏览器缓存后仍可登录；
- 断网时已准备过的工作区可以本地编辑；
- 联网后重新验证身份，再继续上传；
- 退出不会删除未上传队列。

### 7.4 门禁

- 非目标 UID 不能读取业务表；
- 非目标 UID 不能写入业务表；
- 伪造 `user_id` 不能越权；
- 伪造 `user_metadata.username = "W"` 不能获得权限；
- 子表越权查询和跨 owner 引用被拒绝；
- allowlist 不是前端可修改数据。

## 8. 数据迁移和旧账号处理

本方案只简化登录，不自动删除历史业务数据。

执行顺序：

1. 先盘点旧 Auth 用户、旧本地 owner、云端业务记录和未上传队列。
2. 为每个旧工作区建立不含密码和 Token 的业务备份。
3. 明确哪些数据迁入 `W`，哪些隔离保留，哪些确认后删除。
4. 迁移或隔离完成后再停用旧 Auth 用户。
5. 不按账号名称猜测数据归属，不把旧随机 UUID 自动当成新 Auth UID。

如果业务数据去向没有确认，停止删除和覆盖操作，只做只读核验与备份。

## 9. 最小故障处理

| 问题 | 处理 |
| --- | --- |
| Dashboard 的 User Metadata 无法填写 | 留空或填写 `{}`，不影响登录 |
| 密码登录失败 | 核对 Auth 用户、密码、确认状态和项目 URL；不创建本地假会话 |
| 登录成功但无权限 | 核对真实 UID、allowlist 和 schema cache |
| 退出后无法重登 | 核对是否仍使用同一个 Auth 用户，检查前端构建变量是否指向同一项目 |
| 新设备无数据 | 先确认云端已有该 UID 的快照，再检查恢复 RPC 和 UID 门禁 |
| 页面仍显示旧版本 | 核对 Vercel 部署别名、构建提交和 Service Worker 更新 |
| RLS 查询为空 | 分别核对 JWT UID、allowlist、表策略和 Data API GRANT |

任何失败都要记录实际错误和未完成项，不以“本地构建通过”代替真实线上验证。

## 11. 官方依据

- Supabase Password-based Auth：密码登录使用 `signInWithPassword`，认证标识为邮箱或手机号。
- Supabase Sessions：浏览器客户端可以持久化和刷新会话。
- Supabase User Management：用户元数据是可选资料，存放于 `raw_user_meta_data`。
- Supabase Row Level Security：业务数据应以 `auth.uid()` 进行所有权限制。
- Supabase Security Checklist：不能使用可被用户修改的 `user_metadata` 做授权判断。
