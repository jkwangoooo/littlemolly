## 4. 关键设计决策

| 决策 | 理由 |
|------|------|
| 写入前校验放 `localDb.put` / `runTransaction`，不放各 service | 只要还有一个入口不校验，坏数据就能落库。放在唯一写库口才能保证「绕过契约写不进去」，且 `check:local-data` 能静态断言这件事 |
| 事务是**按需提交**的，写入必须在一个同步段发完 | IndexedDB 事务一旦 await 到事务外的 promise 就会先提交。因此查询全部放在事务外做完，`runTransaction` 只收「已算好的写入清单」 |
| 请求级错误必须单独监听（`guardRequest`） | 只挂 `transaction.onerror` 会漏掉仓储层类型/约束错误——它们先在**请求**上触发，没人接就不会传给事务，事务照样 `complete`，表现为「写失败却被当成成功」 |
| 导出宽松（`sanitizeRecord`）、导入严格（`validateRecord`） | v3 迁移有意把老库的 `daily_meals.plan_content`、`day_plans.exercise_content` 留在原地。导出如果严格校验，**老用户一条都导不出来**——恰好是最需要备份的人。清洗只丢新旧写入本来就会丢的字段，丢弃项计入警告 |
| 导入 = 「替换当前账号数据」而不是合并 | 合并需要逐表定义冲突解决规则（同一天两份计划谁赢？），收益与复杂度完全不对称。明确「替换 + 二次确认 + 无法撤销」比模糊的合并诚实 |
| 导入时 `user_id` 一律重映射为当前账号 | 这是「换设备搬家」的唯一实现方式：新设备先注册一个新账号，再导入旧备份，数据就归到新账号名下。同理，`users` 表在导入时跳过（账号由登录/注册管理，不从文件替换） |
| 备份文件里带一条本账号 `users` 记录 | 让文件自洽：导入时能做关联完整性校验，界面也有来源邮箱可显示。它不参与「共 N 条」计数，也不会被写入 |
| 空备份直接拒绝 | 放行等于「用一个空文件清空自己」，风险与收益完全不对称 |
| 备份判定下沉到纯数据模块 `backupFormat.ts` | 浏览器里只能验证「粘贴一段坏文本会报错」，拼不出几十种「差一个字段 / 类型错 / 版本过高 / 引用断裂」的文件。放下沉后 `check:backup` 能在 Node 里逐条断言，且不碰 IndexedDB、不依赖构建产物 |
| 新增解析钩子而不是给源码补 `.ts` 扩展名 | 另两条路都要付代价：补扩展名要在 tsconfig 打开 `allowImportingTsExtensions`（为测试便利改生产配置）；import 构建产物违背「回归脚本不依赖构建产物」。钩子零依赖、只影响脚本进程 |
| `dbSchema()` 辅助不再用无版本号 `open` 「打探」库是否存在 | 无版本号 open 在库不存在时会**凭空造出一个空的 v1 库**，应用随后按最新版本打开时 `oldVersion = 1`，第 1 号迁移被跳过，首批仓库再也建不出来。改为先查 `indexedDB.databases()`，不存在就如实返回、不碰数据库 |

## 6. 本轮修复的缺陷

| # | 缺陷 | 严重度 | 说明 |
|---|------|--------|------|
| 1 | 写入失败可能被当成成功 | 高 | `put` / `remove` 只挂了 `transaction.onerror`；仓储层类型或唯一约束错误先在**请求**上触发，没人接就不传给事务，事务照样 `complete`。新增 `guardRequest` 把请求错误转 reject，并补 `onabort` |
| 2 | 升级被其他标签页占用时界面永久卡住 | 高 | 没有 `onblocked` 回调就只能干等，界面停在「正在保存」且看不出原因。现在直接给出「请关闭其他窗口后重试」 |
| 3 | 一次打开失败后永久失败 | 高 | `databasePromise ??= openDatabase()` 会把 rejected 的 promise 永久缓存，后续每次读写都拿到同一个错误。现在失败即清缓存，用户处理后点「重试」就能恢复 |
| 4 | 本页旧连接会卡住别的标签页升级 | 中 | 补 `onversionchange` 主动关闭并清缓存；让出后本页下次读写重新打开、走一遍迁移，中间没有「读到旧结构」的窗口期 |
| 5 | 跨表写入无原子性 | 中 | 复制昨天要跨 6 张表写几十条，中途失败会留下写了一半的目标日。新增 `runTransaction` |
| 6 | `check:local-data` 误报界面层泄漏 | 低（自伤） | 「界面层没有直接引用 localDb」的裸正则把 `import type { LocalStore }` 也算命中。`BackupCard.tsx` 与 `preferencesLabels.ts` 都是类型导入（编译后擦除，无运行时耦合）。改为只识别值导入后 27/27 通过 |

| 项 | 原因 | 建议处理阶段 |
