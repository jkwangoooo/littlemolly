## 标准更新上线流程

### 1. 接手后先读文档

按顺序阅读：

```text
AGENTS.md
docs/26-S6-handoff-for-codex.md
docs/27-deploy-runbook-for-codex.md
docs/36-版本更新与上线交接说明.md
docs/35-部署凭据与一键发布.md
```

先检查当前工作区，保留用户已有修改，不要使用 `git reset --hard` 或回滚无关文件。

### 2. 版本更新完成后的验收

至少执行：

```bash
npm run typecheck
npm run lint
npm run check:dates
npm run check:local-data
npm run check:backup
npm run check:cloud-parity
npm run check:sync
npm run verify:local
```

改了 PWA 外壳、`vercel.json` 或 `public/_headers`，追加：

```bash
npm run verify:pwa
```

改了 `services/sync/`，追加：

```bash
npm run verify:sync
```

改了数据库迁移或云端 RPC，追加：

```bash
npm run verify:sql
```

`verify:sql` 不要和其他验收脚本并行执行。

### 3. 一句话部署

当 `deploy.env` 已包含全部四项配置，并且 `psql` 可用时，在项目目录执行：

```bash
npm run deploy
```

也可以对负责本项目的 Codex 对话说：

```text
部署最新版本
```

标准脚本 `scripts/deploy.mjs` 会依次执行：

1. `typecheck`、`lint`、`build`、`verify:pwa`。
2. 使用 `SUPABASE_DB_URL` 执行 `deploy/supabase-all-migrations.sql`。
3. 刷新 PostgREST schema cache。
4. 验证 12 张 public 表、3 个 RPC、21 条 RLS 策略。
5. 更新 Vercel Production 的两个 `VITE_*` 构建变量。
6. 部署 Vercel Production。
7. 做首页、SPA 深链接和缓存头自检。

任何一步失败都必须停下并报告真实错误，不能把构建成功说成完整上线成功。

## 当前重要边界

当前已知的外部凭据文件没有确认 `SUPABASE_DB_URL` 是否已经补齐。执行 `npm run deploy` 前先检查是否缺少该字段：

- 缺少 `SUPABASE_DB_URL`：不能执行真实数据库迁移和结构验证，应停下向用户索取 Supabase Database URI。
- 有 `SUPABASE_DB_URL` 但迁移失败：报告原始错误，尤其注意 `auth.users` 触发器权限问题。
- 只有 Vercel 前端发布成功：只能报告“前端已发布”，不能报告“Supabase 已迁移”。
- Vercel 开启 Deployment Protection 时，临时 `*.vercel.app` 地址可能需要认证；优先使用正式域名 `molly.lightwavecommunity.site` 做公开 HTTP 自检。
- 正式域名通过 Cloudflare 访问时，响应头中可能出现 Cloudflare，但缓存规则仍应与 `vercel.json` 一致。

## 失败处理

- `vercel login` 禁止运行，使用 Personal Token 的非交互方式。
- `npx` 首次拉取 CLI 卡住时，先确认网络和本机 npm 缓存；不要误报部署成功。
- 上传完成但没有 `READY`、正式别名或线上 HTTP 自检结果时，不能称为已上线。
- 不要添加 `public/_redirects` 或 `dist/404.html`，否则可能破坏 Service Worker、静态资源和 SPA 回退。
- 不要删除或覆盖用户已有改动；临时验收文件要在确认不需要后清理。
